# Attendance Management System

Attendance presentation conventions for status, timing, filters, dense tables, responsive overflow, empty/loading states, and accessibility are maintained in `docs/ATTENDANCE_UI.md`. Keep that contract aligned with the implementation when changing Attendance views.

Internal HR tool for managing employee attendance, leave, and overtime. Built as a Laravel monolith across 5 phases. This document is the source of truth for tech stack decisions, schema, conventions, and roadmap — keep it updated as each phase lands.

## Tech stack (fixed — do not substitute)

- **Laravel 13** (monolith, no separate API/SPA split)
- **Laravel Breeze** — Blade + Alpine.js stack (auth scaffolding: login, forgot/reset password, password confirmation, profile). Public **registration**, **email verification** and **self-service account deletion** were removed (no route, controller or view for any of them): accounts are provisioned by an admin from the employee form, many have no email at all, and letting a user delete their own account could remove the last admin. `User` never implemented `MustVerifyEmail`, so verification was never enforced; the `verified` middleware is gone from every route. `email_verified_at` itself — vestigial since nothing ever read it — was dropped from `users` entirely in Phase 2.5c, once dropping it stopped costing "a migration for no benefit" (Phase 1's reason to leave it) and started being the last chance to do it for free, before any real deployment made the column permanent. Reintroducing verification would mean re-adding the column, the routes, the contract and the middleware together.
- **Livewire 3** — all interactive server-rendered components (pinned to `^3.0`; do not upgrade to Livewire 4 without a deliberate decision)
- **MySQL** — primary datastore
- **spatie/laravel-permission** — roles (no granular permissions used yet in Phase 1, just roles)
- **Tailwind CSS** (via Breeze) — utility-first styling, no component library

Why: Breeze+Blade avoids standing up a separate frontend/API for what is an internal, low-traffic HR tool. Livewire gives interactivity (search, filters, modals, inline validation) without hand-rolling JSON endpoints or a JS framework. Spatie's package is the de facto standard for Laravel RBAC and plays cleanly with route middleware and policies.

## Local environment

- **The app runs under Docker Compose** (`docker compose up -d`): `app` (PHP 8.5, Composer 2.10), `nginx` (http://localhost:8000), `vite` (Node 22, port 5174), `mysql` (MySQL 9.4, published on host port 3308) and `scheduler` (the same image and environment as `app`, running `php artisan schedule:work` — see "`daily_attendances` builds itself" below). Run every `php artisan`, `composer` and test command **inside the `app` container** (`docker compose exec app php artisan ...`) — that is where the database host `mysql` resolves. Nothing in the current workflow uses a host-native (Homebrew) MySQL; an older revision of this file described one, and the host's `127.0.0.1:3306` has no `stampy` database at all.
- **Testing from a phone or tablet on the LAN:** set `VITE_HMR_HOST` in `.env` to this machine's LAN IP, run `docker compose up -d vite` so the container picks it up, and open `http://<that IP>:8000` on the device. Without it the page asks the device's own `localhost` for Vite's assets and loads unstyled, with no scripts. Unset, it defaults to `localhost`, so nothing changes for anyone else. The IP lives only in the gitignored `.env`; if the router hands out a new one, update it and run `up -d vite` again (reserving the address on the router avoids that). `vite.config.js`'s `cors` allow-list is not mobile-only: setting `server.origin` makes laravel-vite-plugin allow just the Vite origin itself, which blocked `app.js` on `localhost:8000` too, and Alpine then resolved a `close()` call to `window.close` and closed the tab.
- **Timezone:** `config('app.timezone')` is `Asia/Phnom_Penh` (UTC+7, no DST) — not UTC. Every core Attendance rule is a local-time rule (`work_date`'s calendar-day boundary, `in_progress`'s "has end_time passed", the 18h overnight pairing window), and `now()`/`today()`/bare `Carbon::parse()` calls all resolve against this automatically since Laravel sets PHP's default timezone from it at bootstrap — nothing in app code references it directly. **MySQL's own session timezone is a separate setting and currently resolves to `SYSTEM`** (the Docker container's OS timezone, itself UTC) — checked deliberately, not assumed: no query in `DailySummaryBuilder`, `PunchIngestor`, or anywhere else in Attendance depends on it, because every date/datetime comparison (`whereDate`, `whereBetween`, `whereYear`) compares the stored column against a PHP-supplied literal parameter, never MySQL's own `NOW()`/`CURDATE()`/session clock. No connection-level `'timezone'` setting was added because there's nothing for it to fix — but if a future query ever calls a MySQL-side clock function, this stops being true and that query would need explicit handling.
- **Dev database:** `stampy`, in the `mysql` container (user `attendance` / password `secret`; host `mysql` inside the compose network, `127.0.0.1:3308` from the host). The `app` service's `environment:` block in `docker-compose.yml` sets `DB_*` as real environment variables, and **real environment variables outrank every `.env*` file** — so inside the container `.env`'s `127.0.0.1` / `root` values are ignored (they only describe a host-native MySQL this project no longer uses). `docker compose exec app php artisan migrate:fresh --seed` therefore wipes the dev database `stampy`, not a scratch one.
- Run `docker compose exec app php artisan migrate:fresh --seed` to reset and reseed the dev database. Seeded accounts (all password `password`, **change after first login**):
  - `admin@example.com` — admin
  - `aye.aye.mon@example.com` — manager (Engineering)
  - `kyaw.kyaw.naing@example.com` — employee (Engineering)
  - `zaw.zaw.htet@example.com` — manager (Operations)
  - (Su Su Hlaing and Thida Win are seeded as employee records with no login account, to exercise the "employee without a user account" case.)
- **Test database:** the suite runs against MySQL, not sqlite (see phpunit.xml's comment for why — briefly, sqlite has no enforced DATE column type and already hid one real bug). It needs a `stampy_testing` database, separate from the dev `stampy` one, granted to the same `attendance` user. `docker/mysql/init/01-create-testing-db.sql` creates and grants it automatically, but **only on a fresh `mysql_data` volume** — the official MySQL image runs `/docker-entrypoint-initdb.d/` scripts once, the first time the data directory is empty. If you already have an existing volume from before this file existed (e.g. `docker compose up` predates this change), run once by hand:
  ```
  docker compose exec mysql mysql -uroot -psecret -e "
    CREATE DATABASE IF NOT EXISTS stampy_testing CHARACTER SET utf8mb4 COLLATE utf8mb4_unicode_ci;
    GRANT ALL PRIVILEGES ON stampy_testing.* TO 'attendance'@'%';
    FLUSH PRIVILEGES;"
  ```
- **Running the tests:** `docker compose exec app php artisan test` (the whole suite takes seconds, not minutes) or `... php artisan test --filter=SomeTest`. Tests cannot run on the host: `phpunit.xml` pins `DB_HOST=mysql`, which only resolves inside the compose network.
- **Test-database safety (three layers — don't remove any):**
  1. `phpunit.xml` forces `DB_DATABASE=stampy_testing` (`force="true"`; `tests/bootstrap.php` also unsets the container's `$_SERVER` copies so the forced values reach Laravel). PHPUnit's forced values are real environment variables, so **they win over `.env.testing`** for test runs; the two files hold identical values, so they cannot disagree today — if one is changed, change both.
  2. `.env.testing` (committed; contains nothing secret) makes `--env=testing` on an artisan command actually select `stampy_testing`: `docker compose exec app php artisan migrate:fresh --env=testing`. This does not work by itself — the container's real `DB_*` variables would still win — so `bootstrap/app.php` drops them when `--env=testing` is on the command line. Without the flag, artisan still targets the dev `stampy` database, unchanged.
  3. `Tests\TestCase::createApplication()` throws before `RefreshDatabase` can wipe anything if the configured **or** live (`select database()`) database name doesn't end in `_testing`. A run pointed at `stampy` fails every test with "Refusing to run tests".
- **One suite at a time.** `stampy_testing` is a single shared database and `RefreshDatabase` runs `migrate:fresh` on it at the start of every PHPUnit process. Two concurrent runs (or anything else — a seeder, a second agent — writing to it) fail wholesale (`Table 'users' already exists`, nearly every test red) or subtly (a committed seeder row such as the `Software Engineer` position collides with tests that create that same name → `positions_name_unique`). Serial runs are deterministic — checked by running the suite repeatedly in a fixed order, in random order (`php vendor/bin/phpunit --order-by=random --random-order-seed=N`), and with the clock pinned at 20 instants, done by temporarily adding a `setUp()` to `Tests\TestCase` that calls `travelTo(getenv('PIN_NOW'))` and running `docker compose exec -e PIN_NOW='…' app php vendor/bin/phpunit` per instant. The instants: every weekday of 2–8 Feb 2026, times either side of midnight and of the 08:00–17:00 shift (00:00:30, 07:59, 08:11, 16:59:59, 17:00:01, 23:59:30), month and year boundaries (28 Feb/1 Mar, 31 Mar/1 Apr, 31 Dec 2026/1 Jan 2027), a leap day (29 Feb 2028, 1 Mar 2028), and mid-year 2026 and 2030. **Current state (3 Oct 2026): all 20 pass.** An earlier note claimed the same, but it had drifted: 37 tests failed at the early-2026 instants and 4 from 2027 on, because they used fixed Feb–Mar 2026 dates and only passed while the real clock was later in 2026. **The rule that keeps it passing: a test that uses fixed dates fixes its own clock** — `DailySummaryBuilderTest`, `ManualPunchTest`, `HolidayAttendanceTest` and `AttendanceBuildDailyCommandTest` pin it for the whole class in `setUp()`, and a few tests in other classes pin it themselves (`travelTo('2026-04-15 12:00:00')`, after all their data and inside 2026, so `DisplayDate` omits the year); a test relative to `today()` doesn't pin. Repeat the check after touching date-dependent code — Phase 3's leave balances will depend on year boundaries.

## Design system

One primary color, one accent color, one font, a small set of reusable Blade components — with full light/dark support. Apply these everywhere — don't introduce one-off styles. This look (evergreen/mint palette, sidebar + topbar shell, dark mode) was deliberately aligned with a reference UI prototype (`employee-attendance-system-2`, a Next.js/shadcn mockup called "Northstar") that is **not** part of this codebase's stack — it was used only as a visual reference, then re-implemented natively in Blade/Tailwind.

- **Font:** Inter for interface copy, loaded via Bunny Fonts (`fonts.bunny.net`) — set as the Tailwind `sans` default in `tailwind.config.js`. DM Serif Display (also via Bunny Fonts) is used as a single editorial accent — currently only the italicized word in the auth hero headline (`font-serif` utility) — never for body or UI copy.
- **Primary color:** deep evergreen, defined as the `primary` color scale in `tailwind.config.js` (50–900). Use `primary-600`/`primary-700` for buttons/links, `primary-50`/`primary-100` for tints and active-state backgrounds.
- **Accent color:** mint, defined as the `accent` color scale (50–900). Used for icon badges, the brand mark, and highlight text (e.g. the auth hero) — not for primary actions.
- **Neutrals:** the `slate` scale name is kept for continuity, but it is not Tailwind's slate: it is a CSS-variable scale (`resources/css/app.css`, read by `tailwind.config.js`) that is **warm stone in light mode** — matching the warm cream/oklch neutrals in the Northstar reference — and a **neutral, slightly cool zinc in dark mode**, where stone's red-orange cast read as brown. `dark:` classes name a step; the theme picks the hue. Never hard-code a neutral hex: read `--slate-N`. **Readable muted text is `text-slate-500 dark:text-slate-400`** (4.80:1 on a light card, 5.81:1 on a dark one); light `slate-400` is for decorative icons only — see `docs/DESIGN_SYSTEM.md`, Muted text rule. `slate-100` page background / `slate-900` in dark mode, `white`/`slate-800` cards (dark overlays and controls `slate-750`, one step above the card — the full ladder is in `docs/DESIGN_SYSTEM.md`, Dark surfaces), glass sidebar/topbar (see below).
- **Surface architecture:** glass is reserved for application-level shell surfaces: the sidebar, topbar, and authentication shell. The modal backdrop may use transparency and blur as an overlay treatment. Content surfaces are always solid: cards, tables, form controls, dropdowns, popovers, modal panels, and information panels. The `.bg-shell` utility (`resources/css/app.css`) provides the shell's subtle mint/evergreen radial backdrop in light mode; dark mode has no glow, so its neutral surfaces stay clean. See `docs/DESIGN_SYSTEM.md` for the complete v1 rules.
- **Dark mode:** class-based (`darkMode: 'class'` in `tailwind.config.js`), toggled by adding/removing `.dark` on `<html>`. A small inline script in each layout's `<head>` (`app.blade.php`, `guest.blade.php`) applies the stored `localStorage.theme` (or system preference) before paint to avoid a flash of the wrong theme. The toggle button in the topbar and on the auth pages flips the class and persists the choice. Every new component must carry a `dark:` variant — check contrast for text, borders, inputs, and hover states, not just backgrounds.
- **Radius hierarchy:** badges and compact statuses use `rounded-md`; controls and buttons use `rounded-lg`; cards, dropdowns and popovers use `rounded-xl`; modal and large overlay panels use `rounded-2xl`. `rounded-full` is for truly circular geometry such as avatars, dots and progress tracks, not badges or controls.
- **Cards:** `bg-white rounded-xl shadow-sm ring-1 ring-slate-border dark:bg-slate-800` (see `x-card`; the ring is the `border` line token, because a shadow can't separate a card from a dark page) — solid content surfaces with quiet boundaries and no decorative hover treatment.
- **Tables:** row dividers are an inset `h-px bg-slate-divider` line (the `divider` line token — every neutral line is `divider` or `border`, see `docs/DESIGN_SYSTEM.md`, Lines), not a `divide-y` utility — for a real `<table>` (e.g. Employees, Attendance), give the header `<tr>` and every body `<tr>` `relative`, then drop a `pointer-events-none absolute inset-x-6 bottom-0 h-px bg-slate-divider` span into the *last* `<th>`/`<td>` of each row (`@unless ($loop->last)` on body rows, so the final row doesn't get a trailing line before the card edge/pagination) — or, in a table with pinned trailing columns (Employees and Daily Attendance, 640–1279px; see `docs/ATTENDANCE_UI.md`), into the *first* cell with `z-[2]`, since a sticky last cell would become the span's containing block and the line must run above the pinned cells; for a card-style row list with no `<table>` (e.g. Departments, Positions), a plain `border-t border-slate-divider` on each row (`first:border-t-0`) does the same job more simply. Either way it's the **`divider` token** (1.25:1 light, 1.27:1 dark against the card), never a numbered slate step — `slate-100` was nearly invisible against a white card, and ad-hoc values drifted apart. If a new table's borders are hard to see, check the actual color, not just whether a border class is present. `hover:bg-slate-50 dark:hover:bg-slate-750/60` rows, generous cell padding (`px-6 py-4`), uppercase `text-xs` column headers.
- **Links (data rows that navigate elsewhere):** give the link text the primary accent color at rest — `text-primary-700 dark:text-primary-400` — plus a **permanent, muted underline** (`underline decoration-1 underline-offset-2 decoration-primary-300 dark:decoration-primary-700`) that strengthens on hover (`hover:decoration-primary-600 dark:hover:decoration-primary-400`), and a `focus-visible:ring-2 focus-visible:ring-primary-500` on the `<a>` for keyboard users. Color alone was tried first and wasn't enough: in a table where every name in a column is a link, there's no unlinked neighbor to contrast against, so a color-only treatment just reads as that column's styling rather than as interactivity — the underline is what actually reads as "clickable" regardless of neighboring rows. Never rely on a hover-only change (no underline until hover, color-only hover, etc.) — touch devices have no hover state, so whatever signals "link" must already be visible at rest. When a row has a separate record-level destination in addition to its name link, a trailing `chevron-right` must be visible at rest and strengthen on row hover; do not add one when the name is intentionally the sole detail-navigation affordance. Cell links keep the rest of the row selectable, which is the pattern Employees uses; the Attendance tables instead keep the employee name as plain text and make the trailing chevron (visible at rest, 40px, `aria-label` "View attendance for {name}, {date}") the row's only link — see `docs/ATTENDANCE_UI.md`; making a whole row clickable remains valid only when it has no competing actions or selectable operational data. In every case, a link that looks like plain text, or blends into its column, is in practice no link.
- **No interactive element is ever hover-only, full stop — this is the general rule the Links bullet above is one instance of.** Touch devices have no hover state, so whatever signals "this is interactive" and whatever makes it *reachable* must both already be true at rest: not just a link's underline/chevron, but a row's edit/delete icon buttons, an inline "make default" action, any control whose only path to visible or clickable was `opacity-0 … group-hover:opacity-100`. That exact pattern was the default on every list's row actions — Departments, Positions, Holidays, Schedules (edit/delete, and Schedules' "Make default"), the Employees directory table (edit/deactivate/reactivate), and the employee profile's schedule-history delete button — until a manual pass confirmed none of them were reachable at a mobile/touch width and it was removed from all six; the buttons still darken/tint on `hover:bg-*`/`hover:text-*` same as before, that part was never the problem. `group-focus-within:opacity-100` (present on five of the six) looked like it covered keyboard users, but keyboard-focus-only isn't touch-reachable either — it's not a substitute for at-rest visibility, only an addition to it. When adding a new row action, start visible; hover/focus may still *strengthen* the existing look (a background tint, a color shift) but must never be the only way to reveal or reach it.
- **Status vs. timing — two independent dimensions, never conflated:** `AttendanceStatus` answers exactly one question, "did they attend" — `present` / `incomplete` / `absent` / `off` / `holiday` / `leave` / `in_progress`. Whether the *timing* was off (arrived late, left early) is a completely separate fact, tracked on `DailyAttendance`'s `late_minutes`/`early_leave_minutes` columns and surfaced through `isLate()` / `leftEarly()` / `hasTimingException()` — **never** as a status value, and (since Design System v1.1) **never as a colour bucket either**. A `Late` status used to exist and was removed: it mixed the two dimensions, and a day that was both late *and* left early would have needed a third, combined status — the question "what do we call a day that's both?" was itself the sign timing didn't belong in the enum. A `timing` display variant (an amber "Present") was removed in v1.1 for exactly the same reason one level up: one cell colour was carrying two facts. **Principle: a cell or badge colour encodes the attendance STATUS only — one value per day. Attributes that can co-occur on the same day (timing exceptions now, partial leave later) are annotations inside the cell, never the cell/badge colour.** A day both punches cover is always `present`, whatever the timing; a late in-punch on a day that is still `in_progress` or ends `incomplete` keeps that status too (Phase 2.6) — the late annotation rides along, the status and colour don't change. On a holiday every status's timing is forced to 0 by the builder (see the Database schema section's precedence order), so it can never carry a timing annotation.
- **`DailyAttendance::displayVariant()` is the single source of truth for colour** — the one method that maps a day's status to its display bucket, **status-only** (a late Present day is `present`, green). Every view (calendar, table, list) colours a cell/badge by looking up this variant; no view may re-derive a colour bucket by checking `late_minutes`/`early_leave_minutes`/`status` directly. This is what keeps the three views from drifting apart the way they did when each independently decided "does this day have a problem":

  | variant | colour | meaning |
  |---|---|---|
  | `present` | green | normal day |
  | `incomplete` | violet | data defect — a punch is missing |
  | `absent` | red | did not attend |
  | `off` | slate | not a working day |
  | `leave` | accent (mint) | approved leave (Phase 3) — must never read as `off`: a day that used someone's leave balance is not a weekend |
  | `in_progress` | blue | the day is still open and would otherwise be absent/incomplete — an in-only day until first in-punch + 18h (Phase 2.7: past the schedule end and past midnight), a punchless or out-only day today until the schedule end — "not yet", not a failure |
  | `holiday` | fuchsia | a company holiday (see Database schema) |
  | not calculated | muted | no `daily_attendances` row yet — not a variant string (there's no model instance to call it on), handled separately in each view |

  `violet` (`incomplete`) was a deliberate, one-time exception to the app's core green/amber/red/slate palette (plus primary/accent for a couple of low-frequency states) — Incomplete (a device defect — a punch never recorded) and a timing exception (normal employee behavior) used to share amber and were indistinguishable at a glance in light mode. Amber is now reserved for the timing *annotation* (below), which is exactly why Incomplete must not drift back to it. `blue` (`in_progress`) and `fuchsia` (`holiday`) followed for the same reason when Phase 2.4f added both: `in_progress` must not read as red or amber (it means "not yet", not a problem), and `holiday` deliberately avoids primary/accent — both are still green-family hues under this app's palette, which would repeat the exact amber/violet confusability this section already fixed once. Together with `accent` (below) these are the four colors `x-badge` carries beyond its base five (`primary`/`green`/`red`/`amber`/`slate`) — `violet`, `blue`, `fuchsia` and `accent`, nine in all. The `accent` **`x-badge` variant** exists only for `leave` (the accent colour itself is used more widely — the brand mark, icon badges and highlight text, see the Accent bullet above): `text-accent-700 dark:text-accent-300` measured 5.05:1 (light, on `bg-accent-50`) and 8.59:1 (dark, on the badge's `bg-accent-900/30` composited over the card; 8.92:1 on the calendar cell's `/20`), by the same method that reproduces the violet/blue figures above. Don't add another one-off hue for a future variant without the same kind of justification, and don't "clean this up" back to a base color. `text-violet-700 dark:text-violet-300` (light: 6.48:1 on `bg-violet-50`; dark: 7.65:1 on the badge's `bg-violet-900/30` composited over the card, 7.83:1 on the calendar cell's `bg-violet-900/20`), `text-blue-700 dark:text-blue-300` (6.16:1 / 7.56:1 badge, 7.81:1 cell), `text-fuchsia-700 dark:text-fuchsia-300` (5.89:1 / 7.89:1 badge, 8.13:1 cell) — the `-300` in dark mode for all three, not `-400`, for the same reason `absent` uses `red-300`: measured against the actual composited background, not assumed from the shade number.
- **The calendar's status icon and cell fill reflect attendance, not timing — and fill emphasizes exceptions:** a late or early Present day is an ordinary `present` cell with `present`'s check icon — the icon answers "did they show up" (shape-safe in greyscale on its own), while the amber marked time (below) carries the timing exception. A Present cell uses the neutral card surface (no green fill); the green day number and check carry the status, and tinted fills are reserved for the exception statuses (absent, incomplete, leave, holiday, in progress). Off cells are the quietest in the grid: no fill, a medium-weight `slate-500` number, a fainter icon and a dashed boundary. This is presentation only — `displayVariant()` is unchanged and table badges / the day modal's pill stay green. Today is a filled circle behind the day number — the shared filled selected state: white semibold on `primary-600`, dark white on `primary-500` (4.57:1 text, 3.26:1 fill against the dark card) plus `aria-current="date"`, not a cell border — in the calendar only: in the date picker a fill means a chosen date, so today there is a quiet marker (see `docs/ATTENDANCE_UI.md`, Date picker). In-cell times are ≥12px with a ≥10px AM/PM. Conflating "attended" and "arrived late" into one icon (a clock), and later into one amber cell colour, were both earlier, now-removed designs.
- **Marked times and timing values (a specific value is out of range, not just the day):** the timing fact is marked on the value that carries it, in the **timing text** colour — `amber-700` in light mode, `amber-300` in dark mode (`yellow-700` was tried and rejected as muddy; amber only read reddish against the old green-50 Present fill) — **never with an underline — underline is reserved for links everywhere**. In the calendar and the day-detail modal the late In / early Out time is rendered with `<x-time marked>` (`font-medium text-amber-700 dark:text-amber-300`), with an `aria-label` such as "Arrived 16 minutes late"; the medium weight is the non-colour cue alongside the amber, and no extra "+80m" label goes in calendar cells. In tables (the Daily Attendance list and the per-employee table view) In/Out times stay neutral and the **Late / Early values themselves** are amber with the same weight — the column position plus the value-vs-em-dash already make them readable without colour. Measured: `amber-700` is 5.02:1 on white (cards, Present calendar cells) and 4.81:1 on the `slate-50` row hover; `amber-300` is 10.33:1 on the dark card and 9.38:1 on the dark row hover. Amber badges and alerts are a separate role. The red underline this replaced (v1) made a normal late arrival look like an error and borrowed the link affordance. A prior version before that used a plain corner dot; it was removed for saying too little — mark the specific value, not the day.
- **Status badge/pill and Late/Early columns or fields; no timing chips anywhere:** the attendance list, the per-employee table view, and the day-detail modal (`Attendance\Show`) all show the real attendance status ("Present") as **one badge/pill whose colour comes from the status-only `displayVariant()`** — so a late day is a *green* "Present" — and put the timing in the adjacent **Late** and **Early leave** columns or fields (aligned, scannable, amber when non-zero). Every duration shown — Worked, Late, Early, a month's total, the dashboard's Needs attention — goes through `App\Support\Duration::format()` (`21m` under an hour, `1h 20m` from an hour up); counts such as "64 late · 184 early" are not durations and keep their wording. There are **no timing chips anywhere, on purpose**: a `Late 21m` chip repeated exactly what those columns/fields already show — first dropped from the two row layouts for bloating row height (each view's Status cell carries a comment saying so), then from the day-detail modal too once the same reasoning was recognised to apply there as well. The **calendar** has neither chips nor a status word — the cell's fill is the status colour and the amber marked time is the only timing signal.
- **Card headers, avatars, dashboard:** cards have a title-left / muted-meta-right header, and there are no eyebrows anywhere in the app (time scope goes in the meta as real dates; a card whose only heading was an eyebrow gets a real title); initial avatars use one neutral slate tint everywhere, never a status or rotating hue; the dashboard is a stat strip plus two independent column stacks (no row grid, no vertical holes). The dashboard follows the builder's statuses (Phase 2.7) and its rate is attended (present + incomplete) ÷ active employees. In-progress or not-yet-calculated attendance is **pending** and never renders as 0% or as an absence: a `Today`/`Pending` marker with a provisional bar on the trend, `Not calculated` for a past day the builder hasn't finished, `Checked in N / M` per department while pending and `Attended N / M` once closed. Today's strips use live language — `At work N (N late · N past end time) · Left N (N late · N early) · Not in N (N due · N absent · N off · N on holiday · N on leave)`, a partition by punches (in-punch only / has an out-punch / no punches) that always sums to active employees; Not in's sub-line is its exact breakdown by state and always sums to it, the others are timing annotations; never a fourth group — on the Dashboard and on Attendance when the range is exactly today ("Checked in" is reserved for the overlapping "has any punch today" figure on the Department card and trend bar — in or out, so the departments' Checked in always totals At work + Left); status counts are the end-of-day view for other ranges. Full rules in `docs/DESIGN_SYSTEM.md`.

**Alpine note:** any element using a bare `@click`/`x-show`/etc. with no `x-data` anywhere in its ancestor chain silently gets no directive binding at all (confirmed empirically on this Alpine 3.17 setup — it isn't just an edge case). Add `x-data="{}"` directly on any standalone interactive element that isn't already nested inside a component with its own `x-data` (e.g. the dark-mode toggle buttons).

**Blade gotcha: never embed a `@if`/`@endif` (or any other directive) directly inside a self-closing `<x-component ... />` tag's attribute list.** Blade's component-tag compiler (`ComponentTagCompiler::compileSelfClosingTags()`) matches the tag with a regex that only recognizes a fixed set of attribute token shapes — `word="value"`, `:$var`, `@class(...)`, `@style(...)`, `{{ $attributes }}` — and nothing else; a raw `@if (...) autofocus @endif` spliced between attributes doesn't match any of them, so the *entire tag* silently fails to compile as a component and is emitted as literal, uncompiled text instead. No error, no warning — a browser just renders it as an unrecognized custom element and drops the attribute text, so the component appears to vanish. This is exactly what made the profile page's email `<x-text-input>` disappear (it had `@if ($user->employee) autofocus @endif` inline in its attributes). Branch outside the tag instead — two full `<x-component>` calls inside an `@if`/`@else`, the way the Name field right above that same input already did — never a directive inside one tag's attribute list.

**Modals:** every create/edit modal builds on `<x-modal>` (`resources/views/components/modal.blade.php`) — never hand-roll the overlay/backdrop/focus-trap again. `entangle="propertyName"` two-way binds the modal's Alpine `show` state to a Livewire boolean via `$wire.entangle().live`, so Escape and backdrop-click correctly close the Livewire property itself instead of only hiding the panel client-side. Modal panels are always solid and `rounded-2xl`; there is no surface prop. `<x-confirm-dialog>` teleports to `<body>` too, at `z-[60]` — one layer above modals, since a confirmation opened from inside a modal (the day modal's Void) must sit on top of it; at the shared `z-50` the modal, teleported later, covered it. While open it catches Escape on `window` in the capture phase and stops it, so Escape closes the confirmation and not the modal underneath. The shared panel intentionally has no `overflow-hidden`: the employee form applies scrolling to its own body, while panel-level clipping would risk cutting focus rings and overlay content. `maxWidth` only accepts the named presets defined in the component (`sm`/`md`/`lg`/`xl`/`2xl`/`employee-form`) — never interpolate a raw pixel value, since Tailwind's class scanner only picks up literal text in source files and a runtime-built `max-w-[...]` string produces no CSS silently; add a new named preset instead. Focus handling is automatic and has no opt-in: opening always moves focus into the dialog (its `autofocus` field, else the first focusable element), Tab is trapped inside, and closing returns focus to the trigger — see `docs/DESIGN_SYSTEM.md`, Overlays. Never put a `//` comment inside an Alpine `x-init`: it is compiled as an expression and the comment breaks it.

**`<x-modal>` teleports to `<body>` (`<template x-teleport="body">` wrapping its root) — don't "clean this up" back to a plain div.** It guarantees viewport-relative positioning and avoids clipping or containing-block bugs when a modal is rendered within a nested component or shell treatment. `Employees\ScheduleAssignments` is intentionally supported while nested inside `<x-card>` on the employee and profile pages.
Don't swap this for Livewire's own `@teleport`/`@endteleport` either, expecting different behaviour — checked directly in `Livewire\Features\SupportTeleporting`: it compiles to exactly `<template x-teleport="...">`/`</template>`, the same markup, not a different mechanism. The Alpine morph plugin this Livewire version bundles is teleport-aware (`if (from._x_teleport && to._x_teleport) { context.patch(...) } ` in the shipped JS) — verified in a real browser, not just read in the source: typed values in a teleported modal survive an unrelated round-trip on a sibling component *and* two forced round-trips on the same component that owns the modal, a full save-and-close correctly hides the teleported clone (not just the inert original), and five open→save→reopen cycles left exactly one modal instance and one `#dept_name` input in the document throughout, no growth. An older, unrelated revert in this codebase (`f83aa03`, an inline table-row panel, not a modal) cited morph-unreliability as a secondary reason not to bother — its own comment says the actual bug there was something else entirely, and that citation was never itself empirically isolated the way this one now has been. Don't re-raise it without re-testing it.

## Naming conventions

- **Tables/migrations:** snake_case, plural table names, one migration file per table, named `create_{table}_table`. **The interim exception that used to live here is over (Phase 2.5c).** Through Phase 2's testing and bug-fixing, schema changes landed as separate alter-table migrations (`add_*`, `remove_*`) instead, specifically so they'd be picked up by databases that had already run the original `create_{table}_table`; the plan from the start was to fold them back in once that phase ended, and Phase 2.5c did exactly that — five alter-migrations (`add_status_index_to_employees_table`, `remove_deleted_at_from_employees_table`, `add_unique_index_to_department_and_position_names`, `add_voided_at_punched_at_index_to_attendance_logs_table`, `remove_work_schedule_id_from_employees_table`) folded back into `create_employees_table`/`create_departments_table`/`create_positions_table`/`create_attendance_logs_table`, each ending up with the exact final schema those tables already had — verified with a schema dump diff (clean apart from the deliberate `email_verified_at` removal — see Tech stack — and the `migrations` table's own row count) and a SHA-256 hash of every table's substantive data (identical) across a `migrate:fresh --seed` before and after. **From here on, every schema change is its own alter-table migration again — permanently, not another interim phase.** This wasn't just tidiness: consolidation only works because nothing was in production yet. The next schema change might land on a database with real data, where a `create_{table}_table` can't be edited after the fact — a deploy has already run it — so an alter-migration is the only form a change can safely take from now on. Don't fold anything back into a create-migration again without the same reasoning holding (i.e., don't — it won't).
- **Models:** singular StudlyCase (`Employee`, `Department`), relationships as standard Eloquent methods (`department()`, `employees()`).
- **Livewire components:** namespaced by feature under `App\Livewire\{Feature}\{Action}`, e.g. `App\Livewire\Employees\Index`, `App\Livewire\Employees\Form`. Matching views under `resources/views/livewire/{feature}/{action}.blade.php` (kebab-case). A single `Form` component handles both create and edit (mounted with an optional model for edit).
- **Policies:** `app/Policies/{Model}Policy.php`, auto-discovered by Laravel's naming convention (no manual registration needed).
- **Routes:** RESTful names (`employees.index`, `organization.index`), grouped by role-based middleware in `routes/web.php`.

## Coding conventions

- **Validation:** Livewire components validate server-side, via a `rules()` method or an inline `$this->validate([...], [messages])` (as `Attendance\Show::addPunch()` and `Holidays\Index::save()` do) — never trust unvalidated `wire:model` input. The plain controllers are Breeze's auth/profile ones plus `/password/change` (`ForcePasswordChangeController`); they validate inline with `$request->validate([...])` / `validateWithBag()`. Only `LoginRequest` and `ProfileUpdateRequest` are Form Requests, and both are Breeze scaffolding — no feature of ours uses one. Introduce a Form Request only when a plain controller of ours starts handling substantial validated input (e.g. a future API).
- **Authorization:** every Livewire component that manages a resource calls `$this->authorize(...)` in `mount()` for page-level checks and again in the specific action method (e.g. `deactivate()`, `save()`, `delete()`) before mutating. Route groups also carry `role:` middleware as a second layer of defense (see `routes/web.php`). A component that holds the record as a typed model property and has read-only actions (paging, opening a modal) must **also authorize in `render()`**, which every request ends in — `Attendance\Show`, `Employees\Show` and `Employees\ScheduleAssignments` do. Why: those actions are safe today only because Livewire's `ModelSynth` re-derives a typed model property from the signed snapshot and ignores whatever the client sends; that protection is framework behaviour, not this component's, and storing the id as a plain `int` (an ordinary-looking refactor) would silently remove it. It also stops a page opened while authorised from serving data after access is revoked (an employee moved out of a manager's team, say). This applies with no exception to a component nested inside another authorized one, too: `Employees\ScheduleAssignments` is embedded on `Employees\Show`, but it's still its own Livewire component with its own signed snapshot, and an update request aimed at it never routes through the parent's `render()` — so it authorizes in its own `mount()`, its own mutating actions, and its own `render()`, exactly like any standalone component (see the Roles & authorization section, footnote ³, for what each of those three checks).
- **Employee lifecycle:** no soft deletes anywhere in Phase 1 — "deactivate" in the UI only sets `employees.status = inactive`; the row (and its future attendance history) is never removed by the app. Departments/positions with employees assigned cannot be hard-deleted either (guarded in `Departments\Index::delete()` / `Positions\Index::delete()`).
- **User/HR data split:** `users` is auth-only (name, email, password). All HR data lives on `employees`, linked via nullable `employees.user_id` — an employee may exist with no login (not yet onboarded to self-service), and a `User` always optionally has one `Employee` profile. `users.name` is the one exception to "auth-only, independently editable": for a linked user it mirrors `employees.full_name` rather than standing on its own — the name is HR data, and admins own it. The profile page shows it read-only (sourced from the employee record) and `ProfileController::update()` enforces that server-side by dropping any submitted `name` for a linked user, not just hiding the input; `Employees\FormModal::save()` is the other half, copying an admin's changed `full_name` onto the linked user in the same save so the topbar and anywhere else `users.name` appears can't drift from the HR record. An unlinked user (no `Employee` profile) still edits their own name freely.
- **Tests:** `tests/Feature` uses Livewire's `Livewire::test()` harness against components directly (mount/call/assert) for business logic, and plain HTTP tests (`$this->get(...)->assertForbidden()`) for route-level role gating, since Livewire's test harness converts `AuthorizationException` into a response rather than letting it bubble as a PHP exception.

## Testing notes

- **`EmployeeFactory`'s `join_date` is fixed at `2020-01-01`, not random — on purpose.** It used to be random over the last 3 years. Once `addPunch()` validated punch dates against `join_date`, every attendance test that adds a punch on a fixed past date (the suite uses Feb/Mar 2026 dates) failed whenever that employee's random join date happened to fall *after* the punch — about 1 in 5 per test, and with a dozen or so such tests at the time, **7 of 10 full runs failed** (1–5 different tests each time, so it looked like flakiness, not a bug), measured before the default was fixed. A test that needs a particular join date passes `join_date` explicitly; don't restore a random default.
- **Livewire authorization tests:** after a Livewire call is denied by `authorize()`, the response is a 403 rather than a normal component snapshot, so chaining further `->set()`/`->call()` on the same test instance throws `Invalid Livewire snapshot structure`. Assert `->assertForbidden()` on the denied call itself; start a fresh `Livewire::test()` instance for any subsequent assertions.
- **Every `Employee::factory()->create()` needs a default `WorkSchedule` to already exist** (Phase 2.5b) — creation now always assigns one (`Employee::booted()`), and with none, it throws instead of silently succeeding. A test that doesn't otherwise care about schedules still needs `WorkSchedule::factory()->create(['is_default' => true]);` somewhere in its `setUp()` before any employee gets created; deliberately not a global fixture in `Tests\TestCase` (this codebase seeds roles per-file the same way, not globally, and a global default would also break the one test that specifically wants zero schedules to exist, `EmployeeScheduleAssignmentTest::test_creating_an_employee_with_no_default_schedule_creates_nothing_and_throws`).
- **A `scheduleAssignments`/`scheduleOn()` result cached on an `Employee` instance goes stale the moment something *else* writes a new assignment row for that same employee** — `EmployeeScheduleAssigner::assign()` calls `$employee->unsetRelation('scheduleAssignments')` before rebuilding for exactly this reason (see the Database schema section above). The same staleness bites test code: asserting `scheduleOn()` on an `$employee` variable that was already used earlier in the test (including implicitly, e.g. by a component's own `render()` during `Livewire::test()`'s initial mount) needs `->refresh()` first, or it reads the pre-write answer. Several tests in `EmployeeScheduleAssignmentsComponentTest`/`EmployeeScheduleAssignerTest` do this deliberately — it's not defensive paranoia, it reproduces a real failure without it.
- **`DatabaseSeederTest` runs the real `DatabaseSeeder`** (`$this->seed()`, ~3s) and asserts every resulting employee has at least one schedule assignment — a regression test for the exact bug `DatabaseSeeder`'s `WithoutModelEvents` caused (see Roles & authorization's Authorization convention and the Database schema section above): it silently suppressed `Employee::booted()`'s listener, seeding 35 employees with zero assignments and no error anywhere. Confirmed to actually catch it (not just superficially): temporarily reintroducing the trait fails this test, listing all 35 employees by code. If this test ever needs `WorkSchedule::factory()` or similar test setup added ahead of it, that's a sign something *else* now also depends on seed order — don't just silence the assertion.
- **`php artisan make:seeder` generates a class with `use WithoutModelEvents;` by default.** That trait is exactly what caused the bug `DatabaseSeederTest` (above) now guards against — any *new* seeder that creates `Employee` rows and keeps the generated trait will silently skip `Employee::booted()`'s auto-assignment listener the same way, and `DatabaseSeederTest` only covers `DatabaseSeeder` itself, not a seeder added later. Delete the `use WithoutModelEvents;` line (and its `use Illuminate\Database\Console\Seeds\WithoutModelEvents;` import) from any new seeder that touches `employees`, or write that seeder's own regression test the way `DatabaseSeederTest` does.

### Phase 2 (built)

**`work_schedules`**
| Column | Type | Notes |
|---|---|---|
| id | bigint PK | |
| name | string | the one field that stays editable after the schedule is locked (below) |

**Locking, defaults, and validation — all enforced on the model (`WorkSchedule::booted()`), not just the admin form:**
- **Locked once referenced.** Once any `employee_work_schedules` row or `daily_attendances` row references a schedule, `start_time`/`end_time`/`grace_minutes`/`break_minutes`/`workdays` can never change (`WorkScheduleLockedException`) — `DailySummaryBuilder` must always be able to recompute an already-built row identically, which a schedule that keeps changing underneath it would break. To change hours: create a new schedule and reassign the affected employees (`EmployeeScheduleAssigner`, below) — never edit a locked one, even via `tinker`.
- **Once configured, exactly one default remains.** A fresh install may temporarily have no schedules/default while it is being configured, and employee creation fails clearly in that state. Once a default exists, setting `is_default` on another schedule unsets the previous one in the same transaction (`WorkSchedule::save()` wraps every save). The current default can't be deleted or unset directly (`WorkScheduleIsDefaultException`) — either would leave new-employee creation with nothing to assign.
- **Can't delete a referenced schedule** (`WorkScheduleInUseException`) — the same "referenced" test as locking, above.
- **Shape validation** (`InvalidWorkScheduleException`): `end_time` after `start_time`, at least one workday, `break_minutes` shorter than the shift.

**Minute arithmetic truncates, never rounds** — `late_minutes` and `early_leave_minutes` are `intdiv(seconds, 60)` in `DailySummaryBuilder::calculate()`. Concretely, against an 08:00 start with 10 minutes' grace: `08:10:59` is **not** late (grace is inclusive through the whole of minute 10), late begins at `08:11:00`, and `08:11:59` is 11 minutes late, not 12; likewise leaving at `16:59:01` is not an early leave. **This is a deliberate rule, not an oversight — do not "fix" it to `round()` or `ceil()`.** Wherever rounding is ambiguous, attendance favours the employee: docking someone over seconds is indefensible, especially once these minutes feed payroll. `round()` looks more accurate in isolation, and would quietly start marking arrivals from `08:10:30` onward as late. Pinned by `DailySummaryBuilderTest::test_seconds_never_count_against_the_employee_late_and_early_minutes_truncate` (and the grace boundary itself, `>` not `>=`, by `test_arrival_exactly_at_the_end_of_grace_is_not_late`).

**`employee_work_schedules`** (Phase 2.5b) — one row per schedule *change*: the named schedule applies to that employee from `effective_from` until their next row's `effective_from`, or forever if it's their latest. Replaces a single `employees.work_schedule_id` column (removed), which recorded only an employee's *current* schedule — reassigning someone, or editing a schedule's hours, used to silently rewrite already-built history the next time it ran, because `DailySummaryBuilder` always resolved "whichever schedule they're on today," not "whichever schedule was in force on the day being built."
| Column | Type | Notes |
|---|---|---|
| id | bigint PK | |
| employee_id | bigint FK → employees | `cascadeOnDelete` |
| work_schedule_id | bigint FK → work_schedules | `restrictOnDelete` — see the locking rule above |
| effective_from | date | |
| created_by | bigint FK → users, nullable | `nullOnDelete`; who made this assignment (`null` for the automatic one a new employee gets, and for the migration's one-time backfill) |
| timestamps | | |

Unique on `(employee_id, effective_from)`. **No `effective_to` column, deliberately** — storing an end date makes overlaps and gaps possible; deriving it (below) makes both impossible.

**`Employee::scheduleOn(CarbonInterface $date): WorkSchedule`** is the one place this is resolved: the employee's *latest* assignment with `effective_from <= $date`, or their *earliest* one if `$date` precedes every assignment (e.g. `join_date` was edited to something earlier after the fact — every date from `join_date` onward must resolve to *something*). Every place that used to call the now-removed `Employee::effectiveSchedule()` calls this instead, passing the date actually being built — not `today()`. Accessing this (or the underlying `scheduleAssignments()` relation) queries once per `Employee` instance and is cached on it for the rest of the request, so a build run that reuses one `Employee` across many dates (`attendance:build-daily`, `rebuildAround()`/`rebuildFrom()`) only pays for it once — the same memoization pattern as `subordinateIds()`.

**Every employee always has at least one assignment — never a "no row → current default" fallback.** `Employee::booted()`'s `created` listener assigns the current default schedule, effective from `join_date`, in the same transaction as the employee insert itself (`Employee::save()` wraps every *new* row's save in `DB::transaction()`) — a missing default leaves neither row behind, and throws `NoDefaultWorkScheduleException` (the same exception `effectiveSchedule()` used to throw at build time; it's now only reachable at employee-creation time). Existing employees are backfilled the same way, once, by the migration that introduces the table (`App\Support\EmployeeScheduleBackfill`, kept as its own class so the backfill rule is directly testable without exercising the migration file). `NoScheduleAssignmentException` is the separate, should-never-happen case of an employee with zero assignment rows — a data-integrity bug, not a missing-default one. `attendance:import` catches it around its rebuild the same way it used to catch `NoDefaultWorkScheduleException`. `attendance:build-daily` catches it **per employee**, not around the whole run: one employee with no assignment is skipped (not built for any date in the range) and named in the summary, but every other employee in the run still gets built — a single broken employee shouldn't hide whether the other 34 are fine. Still exits non-zero, and still names every affected employee, not just the first.

**`App\Services\Attendance\EmployeeScheduleAssigner`** is the one place an assignment is created or changed outside of that automatic default — the employee profile's per-employee assignment (`Employees\ScheduleAssignments`) and the Schedules tab's bulk reassignment both go through it. `assign()` upserts on `(employee_id, effective_from)` (reassigning at a date that already has a row replaces it, rather than colliding) and always follows with `DailySummaryBuilder::rebuildFrom($employee, $effectiveFrom)` — from the effective date through today, clamped to `join_date` the same way `rebuildAround()` clamps its own D-1/D+1 window (both share a `buildRange()` helper for the actual day-by-day loop). A future-dated assignment rebuilds nothing. `bulkReassign()` moves every **active** employee currently on schedule A (per `scheduleOn(today())`, the same resolution the builder itself uses — not a separate SQL approximation that could drift from it) to schedule B. **A subtlety worth knowing if you touch this again:** `Employee::scheduleAssignments()` caches after first access (see above) — `bulkReassign()`'s own filter step (`scheduleOn(today())` on every candidate) primes that cache on each instance *before* the assignment write, so the write loop explicitly drops it (`unsetRelation('scheduleAssignments')`) before rebuilding; skipping that step silently rebuilds against the *old* schedule.

**The write and the rebuild are two separate steps, in that order, everywhere in this class.** Every assignment row is always safe to write — a single row for `assign()`, or every row for a bulk move, written together in one `DB::transaction()` — while the rebuild that follows can legitimately fail partway (a deploy restart, a DB hiccup, any exception) without corrupting anything, because `daily_attendances` is derived and always recomputable (see above). A rebuild failure is never allowed to roll back or block the assignment write; it's reported (returned as `rebuildError` in the method's array result, e.g. `['days' => int, 'rebuildError' => ?string]` for `assign()`, plus `['employees' => int, ...]` for `bulkReassign()`), logged (`Log::error`), and named with the exact `attendance:build-daily --from=… --to=…` command to heal it, since re-running the same assign/bulk-reassign action is *not* the fix — see the next paragraph for why. `Employees\ScheduleAssignments::assign()` and `::deleteAssignment()` surface `rebuildError` the same way, as a non-blocking amber warning (`addError('rebuild', …)`) rather than a failure, since whatever it names (the assignment change, or the row deletion) already succeeded.

**`bulkReassign()` is capped at `EmployeeScheduleAssigner::MAX_BULK_LOOKBACK_DAYS` (60) days back**, enforced both here and, redundantly, as an inline Livewire validation rule on `Schedules\Index::bulkReassign()` (`BulkReassignmentTooFarBackException` if bypassed) — a bulk move's cost is employees × days rebuilt, unlike a single `assign()`, which has no such cap (rebuilding one employee over a year is still well under a second). Measured on the `stampy_testing` database at realistic scale: 200 employees 60 days back took ~15s; 200 employees 365 days back took ~88s, past nginx's default 60s `fastcgi_read_timeout` in this app's own docker-compose stack, with no PHP-side execution-time limit to stop it running and no `ignore_user_abort()`, so the request is simply cut off mid-work once nginx gives up — the cap exists so that's found here, not by a slow production request. **Why every assignment is written before any rebuild starts, specifically for the bulk case:** if writes and rebuilds were interleaved per employee and something failed partway (some employees moved, some not), retrying the same bulk move wouldn't heal it — the already-moved employees no longer match "currently on schedule A" and wouldn't be selected a second time, so the one whose rebuild was cut off would never be reached again. Writing every assignment first makes the operation retry-safe for that half unconditionally; only the rebuild can still fail, and *that's* healed by running the named `attendance:build-daily` command over the stated range (idempotent, safe to re-run), never by calling `bulkReassign()` again. With a 60-day cap, the stale window a failed rebuild can leave can reach 60 days — well past the nightly scheduled rebuild's own 7-day healing window (see "`daily_attendances` builds itself" below) — so it's surfaced and logged rather than left to heal itself.

**Known, accepted limitation: the on-screen `rebuild` warning is a one-shot Livewire validation error, not a durable notice — it disappears after the very next Livewire round-trip, not just on navigation.** `Employees\ScheduleAssignments::assign()`/`::deleteAssignment()` surface `rebuildError` via `addError('rebuild', …)`, which Livewire's error bag only carries in the response for the request that set it; confirmed empirically (not assumed): a test that forces the failure, asserts the error is present, then performs one *unrelated* `set()` on the same component instance — nothing to do with validation — finds the error gone. So if the admin doesn't read the amber banner in that exact instant (closes the modal and immediately does anything else that fires a Livewire request — scrolls past a lazy-loaded section, another component's poll, an unrelated click), it vanishes with no trace in the UI. This is safe, not silent data corruption: the assignment write always lands first and is never rolled back (see above), so only `daily_attendances` can be stale, and the durable record is the `Log::error()` line, not the UI banner:
  - `assign()`: `"Schedule assignment for {employee_code}: rebuild failed partway ({exception message}). Not every affected day may have been rebuilt. Run: php artisan attendance:build-daily --from={effective_from} --to={today} --employee={employee_code}"`
  - `bulkReassign()`: `"Bulk schedule reassignment: rebuild failed partway, after all {N} assignment(s) were already written ({exception message}). Not every affected day may have been rebuilt. Run: php artisan attendance:build-daily --from={effective_from} --to={today}"`
  - `deleteAssignment()`: same shape as `assign()`, `"Schedule assignment deletion for {employee_code}: rebuild failed partway (…). …"`

  Grep the log for `rebuild failed partway` and run the `attendance:build-daily` command it names — that's the fix regardless of whether anyone saw the banner. Note the nightly scheduled rebuild only heals the last 7 days (see "`daily_attendances` builds itself" below), so a failure older than that stays stale until someone runs the command by hand. If rebuild failures turn out to happen in practice (not just in tests), revisit this with a state-driven approach instead of a one-shot flash: record the failed range somewhere durable, retry it from the scheduled task, and show a banner that stays up until it's actually healed rather than until the next click.

Measured at 208,800 punches (200 employees × ~2 years): `type: ALL` becomes `type: ref` with a backward index scan and no filesort, ~66 ms down to ~0.11 ms. Don't drop it as redundant with the unique index; it isn't.

**Punches and builds can't reach outside real time.** `Attendance\Show::addPunch()` rejects a punch dated before the employee's `join_date`, dated after today, or timed later than the current time today (exactly "now" is allowed), each with a message naming the constraint. `attendance:build-daily` rejects any `--date`/`--from`/`--to` after today with an error and exit code 1 — it never silently clamps the range, so an operator who typed 2030 is told (today itself is allowed: that's what `in_progress` is for); days before an employee's `join_date` are skipped for that employee, not errored. Why: both used to accept any date, and a punch 30 days before hire, or a build for 2030 (35 `absent` rows for a date that hadn't happened), wrote real-looking `daily_attendances` rows into the one table treated as derived truth, with no way afterwards to tell invented rows from real ones.

**The CSV import path doesn't assume a well-formed file** (`CsvAttendanceSource`, driven by `attendance:import`). A row whose field count differs from the header (a truncated final line, a trailing comma), a missing `device_user_id`/`punched_at`, or a date that doesn't exist (`2026-02-30`, month 13, hour 25) is recorded in `errors()`, skipped with its line number, and printed in the import summary — every other row still imports. Impossible dates are caught by `App\Support\StrictDate`, because `Carbon::createFromFormat` silently rolls them over (`2026-02-30` becomes `2026-03-02`), which would write a plausible-looking wrong punch into the append-only log that nothing downstream could ever detect. It checks PHP's parse warnings rather than doing a strict round-trip, so real but unpadded input like `2026-1-5` is still accepted. `attendance:build-daily`'s `--date`/`--from`/`--to` use the same check. Two file-level cases abort with a clear `AttendanceImportException` instead: an error the reader didn't anticipate (e.g. a bad `punch_type_map` value) names the line it happened on, and an unopenable file says "Unable to open attendance CSV" — its `fopen()` is `@`-suppressed on purpose, since Laravel would otherwise turn the warning into an `ErrorException` before that check could run.

**`daily_attendances` builds itself** (Phase 2.5a). Before this, a row existed only if someone ran `attendance:build-daily` by hand, so the dashboard read "Not calculated", and a day built as `in_progress` never became `absent`/`incomplete` because nothing rebuilt it after `end_time`. Now, in `App\Console\AttendanceSchedule` (wired through `withSchedule()` in `bootstrap/app.php`), run by the `scheduler` service against the dev `stampy` database, in the app timezone:
- **Every 15 minutes: today** (`attendance:build-daily --date=<today>`). This is what moves an `in_progress` day to its final status once it closes, and picks up punches imported during the day.
- **Every 15 minutes, while yesterday has any `in_progress` row: yesterday** (Phase 2.7, `--date=<yesterday>`, gated by a `when()` checked on each tick). An in-only day closes at first in-punch + 18h, which can be after midnight (a 9:30 in-punch closes at 03:30); this closes it within 15 minutes instead of waiting for 02:10 — or, for that 9:30 punch, the next night.
- **Daily at 02:10: the last 7 days** (`--from=<today−6> --to=<today>`) — a window, not just yesterday. The command's default range is yesterday and today, so if the server were down for three days those days would never be built; the builder is idempotent, so re-running a week costs nothing and heals any gap inside the window with no state to track.
- All three use `withoutOverlapping()`, with the lock capped (10, 10 and 60 minutes) so a killed run can't block its task for the 24h default. A non-zero exit is logged with the command's output: `Log::error("Scheduled attendance rebuild (…) failed: …")`. The dates are computed when the schedule is registered, which is every minute (`schedule:work` starts a fresh `schedule:run` per tick), so "today" is never stale. Evidence it runs: `docker compose logs scheduler`; what's registered: `docker compose exec app php artisan schedule:list`.
- **Gaps older than 7 days are not healed automatically** — nothing else would ever come back for them, and more machinery isn't worth it. Backfill by hand: `docker compose exec app php artisan attendance:build-daily --from=YYYY-MM-DD --to=YYYY-MM-DD` (never in the future; for one employee add `--employee=<id or code>`).

**An import rebuilds what it touched, once, at the end** (`attendance:import`). The range is the earliest to the latest newly imported `punched_at` date, widened by one day each side (an imported punch can pair into the previous day through the 18h overnight window, and change the next day's "claimed by an earlier shift" result), for **every active employee** — so someone with no punches in the window is marked absent rather than left "not calculated". The summary prints the range. `--dry-run` rebuilds nothing, and an import that adds nothing (all duplicates) rebuilds nothing. If the rebuild fails (`NoScheduleAssignmentException` — see the `employee_work_schedules` section above; not a missing default, which can only happen at employee-creation time now) the punches are kept (they're already written), the command exits 1 and says to run `attendance:build-daily` once that's fixed.

**The D-1/D/D+1 window has one home** — `DailySummaryBuilder::rebuildAround()`, used by both a manual punch (`Attendance\Show`) and an import — and it is clamped to the employee's real history: never before `join_date`, never after today. The clamp exists because the old manual-punch copy of this rule was not clamped: a punch added today on someone's hire date created a row for the day *before* they were hired (`off`) and a row for *tomorrow* (`absent`), the same invented-row defect as the date-range rules above. (This clamps a window the code derives, not a range the operator typed, so it doesn't conflict with `build-daily` refusing to silently clamp an operator's dates.)

Three model decisions here aren't obvious from the schema alone, and have already been re-litigated at least once — recorded so they aren't re-opened again:
- **`attendance_logs` is append-only.** A correction is a void (`voided_at`/`voided_by`) plus a new row, never an edit to an existing one — preserves a full audit trail of what the device actually reported vs. what an admin corrected, and is what makes `daily_attendances` safely recomputable at any time.
- **Status answers "did they attend"; timing is a separate dimension.** `AttendanceStatus` has no `Late` value — a day with `late_minutes`/`early_leave_minutes` > 0 keeps its own status (`present`, or, since Phase 2.6, `in_progress`/`incomplete` for late), and a holiday's timing fields are forced to 0 by the builder for every status, so it can never register as a timing exception either. **Timing does not need both punches:** late is a fact about the in-punch (the `first_in` the builder's pairing already chose) and is recorded as soon as it exists, and it never disappears when an `in_progress` day later becomes `incomplete`; early leave is a fact about the out-punch of a worked shift and is only recorded on `present` days. An out-only day has neither. See the "Status vs. timing" note under Design system for the full reasoning; `DailyAttendance::displayVariant()` is what every view colours from, so this distinction isn't just a data-modeling footnote — it's the one thing every Attendance view must route through.
- **Status precedence, highest to lowest** (`DailySummaryBuilder::calculate()`, where the full comment lives): **(1) `off`** — no punches at all and not a scheduled workday, holiday or not. **(2) `holiday`** — no punches at all, a workday, holiday-marked. **(3) `present`** — both punches exist, on any day; a holiday only zeroes its timing, it doesn't need to override the status. **(4) `in_progress`** — the day is still open, and punches so far would otherwise resolve to (5) or (6). Since Phase 2.7 "open" depends on the punches: an in-only day stays open until its pairing window closes (first in-punch + `MAX_SHIFT_HOURS`, 18h — past the schedule end and past midnight, so someone on overtime is still at work and a (+1) out-punch turns the day `present` with no `incomplete` in between); a punchless or out-only day is open only today, until the schedule's `end_time`. **(5) `incomplete`** — exactly one of {in, out}, on any day, holiday or not — a missing punch is a device-defect fact independent of whether the day was a holiday. Precedence did not change in Phase 2.6; only which statuses can carry `late_minutes` did (see the bullet above). **(6) `absent`** — a workday, no punches, none of the above applied. Someone who works a non-workday (an ordinary weekend or a weekend holiday) is (3), not (1) — that already worked before holidays or in_progress existed and neither changes it.
- **Known, accepted limitation: a same-day in/out pair more than 18h apart shows as `incomplete`.** `MAX_SHIFT_HOURS` (18) bounds how far after an in-punch an out-punch may be and still pair with it. An in at 00:00:00 and an out at 23:59:00 on the same day are 23h59m apart, so the out is never paired: `last_out` is null, `worked_minutes` is 0, status is `incomplete` — and nothing on the row records that an out-punch existed and was excluded. This is the window working as designed, not a bug. The punch itself is intact in `attendance_logs` and listed in the day's raw punches on `Attendance\Show`, so if you're debugging an inexplicable `incomplete`, look there for an out-punch more than 18h after the in-punch. Deliberately no "excluded punch" indicator for now; revisit only if genuine ~24h shifts turn up.
- **Known, accepted limitation: no overnight schedules.** `WorkSchedule` rejects `end_time <= start_time` outright (`InvalidWorkScheduleException`) — `DailySummaryBuilder`'s late/early-leave arithmetic (`calculate()`) assumes a shift starts and ends within the same calendar day; a genuinely overnight schedule (say 22:00–06:00) would compute silently wrong numbers rather than fail loudly. Like the 18h limitation above, this is a deliberate boundary of what the builder supports today, not an oversight — revisit only if a real night-shift schedule is needed, and treat it as a builder change, not just a validation relaxation.

Only the mutating actions (`create`/`assign`/`deleteAssignment`) additionally check `EmployeePolicy::update` (admin-only), the same ability that already gates manual punches, password resets and editing the employee record itself — a manager sees the history but no assign/delete controls. `EmployeeScheduleAssignmentsComponentTest::test_a_page_opened_while_authorized_stops_serving_data_once_access_is_revoked` constructs the mid-session-revocation scenario against this component directly, the same way `EmployeeShowTest`'s identically-named test does for the parent.

**A link, card or row shown to someone who cannot open its target is a bug, whether or not it ever gets clicked — and the fix is always to gate by the ability the destination itself enforces, never a role list at the call site.** A role list at the call site and the destination's real gate are two independent facts that only happen to agree today; the first time someone changes one without the other, they drift, and the UI keeps offering a route that 403s. Found and fixed this way three times so far, each a slightly different shape of the same mistake: the Employees directory originally listed every employee to every manager rather than scoping rows to their own team, fixed by routing every list through `EmployeeScope` (¹ ² above) instead of a per-page role check; `Attendance\Show`'s "Back to attendance" link rendered unconditionally, including via `/my-attendance`, which no `role:` middleware or policy would have caught since the component itself is reachable by everyone — fixed by gating on the route actually reached (`request()->routeIs('attendance.mine')`), not a role; the dashboard's "Quick Actions" card rendered all four of its links whenever `$stats` was set, which is true for `admin` **or** `manager`, while two of those links (`organization.index`) are `role:admin` only — fixed by filtering each action through `$user->can(...)` against the exact ability (`EmployeePolicy::create`/`viewAny`, `DepartmentPolicy::viewAny`) its destination page itself checks in `mount()`, and hiding the whole card rather than leaving a manager with one action that only duplicates a sidebar link they already have. When adding a new link, card or row: ask what ability its destination checks, and gate on that ability directly — not on whichever role happens to reach the page today.

Editing employees, punches, holidays and the like is admin-only through `update`/`create`/`deactivate`/`delete` on the policies; `EmployeePolicy::update` is also what gates manual punches and password resets. Separately, every signed-in route except password change and logout is blocked while a user's `must_change_password` is set (the global `EnsureMustChangePassword` middleware).

Enforced in four places, none of which is optional:
1. **Route middleware** — `role:admin|manager` / `role:admin` groups in `routes/web.php`. `/my-attendance`, `/profile` and the password routes need only a signed-in user (`auth`); there is no `verified` middleware anywhere (see Tech stack).
2. **Policies, via `$this->authorize(...)` in Livewire components** — in `mount()`, again in every mutating action, and in `render()` for `Attendance\Show`, `Employees\Show` and `Employees\ScheduleAssignments` (see the Authorization convention, and ³ above for why the last of those skips the `mount()` check the other two have).
3. **Row-level query scoping** — `EmployeeScope`, used by the attendance list, the employee directory and the dashboard's attendance figures, per ¹.
4. **The UI** — the sidebar (`hasRole(...)`) and `@can` in Blade hide controls a user can't use. This is presentation only; it is never the gate, and a hidden button must always be backed by an `authorize()` in the action.

## 5-phase roadmap

1. **Foundation** (complete) — project setup, auth, roles/permissions, departments, positions, employees, layout/navigation. Closed out with a full codebase audit (see `AUDIT.md`) — all Critical/High/Medium findings fixed.
2. **Attendance & device integration** (complete) — `attendance_logs` ingestion (CSV import for now — see "ZKTeco device ingestion" below), processing into `daily_attendances`, attendance dashboards/reports, effective-dated schedules, holidays, row-level manager scoping.

5. **Reporting & polish** — cross-cutting reports (attendance/leave/overtime), exports, UX polish, performance pass.

A new phase's scope is written into this file *before* it's built, same as Phase 2's own scope was — Phase 3 hasn't had that pass yet, so nothing under it should start until it does.

**Phase 2, complete.** What shipped, at the level someone picking this up needs — the Database schema and Design system sections above already have the full detail, this is the map, not a re-explanation:
- **Ingestion:** CSV import (`attendance:import`) — see "ZKTeco device ingestion" immediately below for why, and exactly where a real device plugs in later.
- **Processing:** `DailySummaryBuilder` turns raw punches into one `daily_attendances` row per employee per day, with status and timing kept as two separate dimensions (see "Status vs. timing" under Design system) and a fixed precedence order for which status wins on a given day. Rebuilds happen on a schedule (Phase 2.5a) — every 15 minutes for today, nightly for the last 7 days — so `attendance:build-daily` is a backfill tool for gaps older than that, not something routine operation depends on running by hand.
- **Schedules:** effective-dated (Phase 2.5b, `employee_work_schedules`) — reassigning someone, or editing a schedule's hours, never rewrites already-built history. Admin CRUD, locking, defaults, and single/bulk reassignment (with a preview of who's affected) live on the Schedules tab under Organization.

**ZKTeco device ingestion is deliberately deferred, not forgotten.** No device or a real export from one has been available to build against — `config/attendance.php`'s CSV column mapping and `datetime_format` are explicitly placeholder, tuned to whatever sample data existed, not a real device's actual output (its own comment says so). The seam is already in place for when one is: `App\Contracts\AttendanceSource` is the one-method interface (`punches($from, $to): iterable<PunchRecord>`) a device-based source implements alongside `CsvAttendanceSource` — `PunchIngestor` (the single write path into `attendance_logs`, per its own doc comment) doesn't care which source it's fed. Three things to check when a real device or export shows up, not before:
  - `attendance_logs`' unique index (`employee_id`, `punched_at`, `source`) doesn't include `device_id` — fine with one device (today `PunchIngestor` writes `device_id => null` unconditionally, since there's only ever been one CSV "source" to distinguish), but worth revisiting once a second physical device exists and two genuinely different punches could otherwise collide on the same key.
  - The CSV `datetime_format` (`config('attendance.csv.datetime_format')`, currently `'Y-m-d H:i:s'`) needs checking against whatever format the device's real export actually uses — it was never derived from one.
  - `PunchIngestor::inferMissingPunchTypes()` (alternation with a double-tap window, see its own doc comment) is currently a fallback for CSV rows with an unmapped `state` column — many biometric terminals don't report in/out at all, relying on alternation entirely, which would make this inference the *primary* path rather than an edge case once a real device is wired in. Worth a closer look at that point, not a rewrite now.

**Phase 2.6, built: live today — late on the in-punch, "Not in yet".** Problem: late minutes were only computed once a day had both punches, so a late arrival was invisible while the day was in progress (the dashboard's Needs attention stayed empty mid-day), and employees who hadn't arrived yet were hidden inside `in_progress`. Owner decisions:
1. `late_minutes` is computed whenever the day has an in-punch — `in_progress`, `incomplete` and `present` — and stays on the row when an `in_progress` day later becomes `incomplete`: a late fact never disappears.
2. `early_leave_minutes` stays present-only (it isn't knowable before the out-punch).
3. A day with only an out-punch has no late (no in-punch) and no early leave.
4. The holiday rule extends: on a holiday-marked day timing is forced to 0 for `in_progress` and `incomplete` as well as `present`.
5. Status is unchanged: no new `AttendanceStatus` value, precedence unchanged, `displayVariant()` unchanged (colour = status only). Late stays an annotation.
6. **"Not in yet" is a derived display fact, never a status and never "absent":** an `in_progress` row with no punches whose schedule `start_time + grace_minutes` has passed (app timezone). Before that point the person is simply in progress.
7. Grace and truncation are unchanged (late begins strictly after grace; `intdiv`, never round).
8. The builder's existing in/out pairing decides which punch is the in-punch; no second pairing rule.

Scope: `DailySummaryBuilder::calculate()` (1–4, 7–8) with its comment and this file's schema/precedence wording updated; `isLate()`/`hasTimingException()` follow the new `late_minutes`, `leftEarly()` unchanged; a backfill of historical incomplete days with the existing `attendance:build-daily` (no migration); UI — the Attendance table's Late column and the "Late arrival" filter include `in_progress`/`incomplete` rows, the calendar/modal mark the in-time on those days, the dashboard's Needs attention lists late arrivals today then "Not in yet · due 8:00 AM" (Phase 2.7 later put Absent and Incomplete first — see `docs/ATTENDANCE_UI.md`, Needs attention), and the live strip shows a late sub-line on At work and Left (an annotation on a partition group, never a fourth group) with the dashboard's Employees cell removed and three cells in one row at every width. "Not in yet" has two documented scopes: the strip counts every active employee with no punch yet today; Needs attention lists only those past `start_time + grace_minutes` — always a subset of the strip's count, never a different definition under the same label.

**Phase 2.7 — Day close (built).** Problem: after a schedule's end time the builder closed every row at once — an in-punch-only row became `incomplete` at 17:00 even when the person was still at work on overtime, although the builder would still pair an out-punch up to 18h after the in-punch (the "(+1)" overnight out); and the dashboard, once today's rows were final, contradicted itself (a live "Not in yet 35" strip beside 8 Absent rows, 0% bars with no marker). Owner decisions:
1. **An in-only row stays `in_progress` until its pairing window closes** — first in-punch + `MAX_SHIFT_HOURS` (18h), even past the schedule's end and past midnight — and only then becomes `incomplete`. This keeps overtime workers "at work" and matches the existing out-punch pairing exactly, so an out at 00:42 (+1) turns the row `present` with no `incomplete` in between.
2. A row with **no punches** still becomes `absent` at the schedule's end (unchanged); an out-only row keeps its rule (today, before end).
3. Late on `in_progress` rows stays as Phase 2.6 made it; early leave still needs both punches.
4. **Scheduler:** the 15-minute job also rebuilds **yesterday** while yesterday has any `in_progress` row, so a late in-punch (9:30 → window closes 03:30) is closed without waiting for the 02:10 run.
5. **The dashboard follows the builder's statuses** — one source of truth, consistent with the attendance table: an Absent row shows as Absent. The live strip's third cell becomes **"Not in"** (active employees with no punches today — the strip is a partition by punches, so an out-only day is Left) with a sub-line by state — `{n} due` (punchless `in_progress`, plus anyone not built yet), `{n} absent`, both when mixed; **"At work"** adds `{n} past end time` for `in_progress` rows whose schedule end has passed. The partition and its sum rule are unchanged. Needs attention shows "Not in yet · due 8:00 AM" only for punchless `in_progress` rows past start + grace, an Absent badge for Absent rows, and its header shows the real total (the list stays capped at 8, most urgent first).
6. **Attendance rate = attended ÷ active employees, attended = present + incomplete**, for the trend bars and the Department card. A day with any `in_progress` row is pending: a lighter bar of attended so far (anyone with a punch, in or out) and a marker — "Today" for today, "Pending" for an earlier day still inside a pairing window. The Department card says "Checked in N / M" (any punch today, so the departments' total equals the strip's At work + Left) while pending and "Attended N / M" once closed — no bare percentage. A closed workday with 0 attended shows a small "0%" marker. A past day with no rows, or with `in_progress` rows whose window has already closed (the builder didn't run), shows a muted "Not calculated" marker — never 0%, never Absent. **"Active" means active now**, in the numerator as in the denominator: the trend and `todayIsPending()` count only rows of employees whose `status` is `active` today, so a deactivated employee's past days drop out of the 7-day trend (they used to stay in the numerator while leaving the denominator, lifting a past bar — even past 100%). Keeping them for the days they were still employed would need a deactivation date, which doesn't exist — see Open questions for Phase 3.

Scope: `DailySummaryBuilder::calculate()`/`isInProgress()` and its precedence comment; `App\Console\AttendanceSchedule`; `DashboardAttendance` (strip, needs attention, trend, departments) and the dashboard view; the `in_progress` definition everywhere it's documented (this file's `displayVariant()` table and precedence, `docs/ATTENDANCE_UI.md`, `AttendanceStatus`); tests for each rule above.

## Open questions for Phase 3

Surfaced during Phase 2's closeout review. Not decided — recorded so Phase 3's actual scoping pass (see the roadmap above: scope goes in this file before building) starts from these instead of rediscovering them.

- **Leave days vs. "Calculated workdays".** `Attendance\Show::summary()`'s `workdays` count is `present + absent + incomplete` only (see the Database schema section's `daily_attendances` status precedence) — `off`, `holiday`, and the not-yet-built `leave` status are all excluded identically. That's consistent today, but once `leaves` exists and a day can actually resolve to `leave`, an approved leave day won't count as a workday either, which breaks the obvious phrasing ("3 of 22 workdays taken as leave" implies leave days ARE workdays, just ones not worked). Needs an explicit decision once leave exists, not an assumption either way.
- **Where attendance-rule settings live.** Organization currently holds Departments, Positions, Holidays and Schedules — four tabs of org structure. Leave types and overtime rules are a different kind of thing (attendance *policy*, not org *structure*); adding them as two more tabs would get to six and start blurring that distinction. Worth splitting into a separate settings area once Phase 3/4 need somewhere to put them — not worth restructuring Organization now, before there's a second thing to put there.
- **The employee dashboard is empty.** A non-admin, non-manager user sees a greeting and nothing else (`routes/web.php`'s dashboard route only builds `$stats`/`$attendance` for `admin`/`manager`). The data to show them their own summary already exists — it's the same shape `Attendance\Show`'s own `summary()` produces for `/my-attendance` — this just hasn't been wired to the dashboard yet.
- **A deactivation/termination date.** `employees.status` is a flag with no date, so every attendance figure scoped to "active" means *active now*: the dashboard's 7-day trend drops a deactivated employee's past days entirely (Phase 2.7, item 6), rather than counting them for the days they were still employed. Leave balances, accruals and pro-rating will need to know when employment ended, so whether to add an effective deactivation date (and backfill it) belongs in Phase 3's scoping, not a silent workaround now.
- **How payroll treats `late_minutes` on incomplete days.** Since Phase 2.6 a late arrival is recorded on an `incomplete` day too (the in-punch exists, the out-punch doesn't). The fact is recorded; whether payroll deducts for it when the day itself is a device-defect `incomplete` is undecided.
- **One approval engine, not three.** Leave requests, overtime requests, and (eventually, maybe) punch-correction requests are the same shape: an employee requests something, their manager approves or rejects it, a record changes as a result. Building each as its own bespoke request/approval flow would produce three inconsistent implementations of the same rule. `employees.manager_id` and `EmployeePolicy`'s transitive subordinate scoping (`isManagerOf()`/`subordinateIds()`, see Roles & authorization footnote ¹) already exist and are exactly the primitive a shared approval engine would be built on — worth designing one engine when Phase 3 starts, not bolting leave approval on ad hoc and rebuilding for overtime in Phase 4.

# Attendance Management System

Attendance presentation conventions for status, timing, filters, dense tables, responsive overflow, empty/loading states, and accessibility are maintained in `docs/ATTENDANCE_UI.md`. Keep that contract aligned with the implementation when changing Attendance views.

Internal HR tool for managing employee attendance, leave, and overtime. Built as a Laravel monolith across 5 phases. This document is the source of truth for tech stack decisions, schema, conventions, and roadmap — keep it updated as each phase lands.

## Tech stack (fixed — do not substitute)

- **Laravel 13** (monolith, no separate API/SPA split)
- **Laravel Breeze** — Blade + Alpine.js stack (auth scaffolding: login, forgot/reset password, password confirmation, profile). Public **registration**, **email verification** and **self-service account deletion** were removed (no route, controller or view for any of them): accounts are provisioned by an admin from the employee form, many have no email at all, and letting a user delete their own account could remove the last admin. `User` never implemented `MustVerifyEmail`, so verification was never enforced; the `verified` middleware is gone from every route. `email_verified_at` itself — vestigial since nothing ever read it — was dropped from `users` entirely in Phase 2.5c, once dropping it stopped costing "a migration for no benefit" (Phase 1's reason to leave it) and started being the last chance to do it for free, before any real deployment made the column permanent. Reintroducing verification would mean re-adding the column, the routes, the contract and the middleware together.
- **Livewire 3** — all interactive server-rendered components (pinned to `^3.0`; do not upgrade to Livewire 4 without a deliberate decision)
- **MySQL** — primary datastore
- **spatie/laravel-permission** — roles (no granular permissions used yet in Phase 1, just roles)
- **Tailwind CSS** (via Breeze) — utility-first styling, no component library

Why: Breeze+Blade avoids standing up a separate frontend/API for what is an internal, low-traffic HR tool. Livewire gives interactivity (search, filters, modals, inline validation) without hand-rolling JSON endpoints or a JS framework. Spatie's package is the de facto standard for Laravel RBAC and plays cleanly with route middleware and policies.

## Local environment

- **The app runs under Docker Compose** (`docker compose up -d`): `app` (PHP 8.5, Composer 2.10), `nginx` (http://localhost:8000), `vite` (Node 22, port 5174), `mysql` (MySQL 9.4, published on host port 3308) and `scheduler` (the same image and environment as `app`, running `php artisan schedule:work` — see "`daily_attendances` builds itself" below). Run every `php artisan`, `composer` and test command **inside the `app` container** (`docker compose exec app php artisan ...`) — that is where the database host `mysql` resolves. Nothing in the current workflow uses a host-native (Homebrew) MySQL; an older revision of this file described one, and the host's `127.0.0.1:3306` has no `stampy` database at all.
- **Testing from a phone or tablet on the LAN:** set `VITE_HMR_HOST` in `.env` to this machine's LAN IP, run `docker compose up -d vite` so the container picks it up, and open `http://<that IP>:8000` on the device. Without it the page asks the device's own `localhost` for Vite's assets and loads unstyled, with no scripts. Unset, it defaults to `localhost`, so nothing changes for anyone else. The IP lives only in the gitignored `.env`; if the router hands out a new one, update it and run `up -d vite` again (reserving the address on the router avoids that). `vite.config.js`'s `cors` allow-list is not mobile-only: setting `server.origin` makes laravel-vite-plugin allow just the Vite origin itself, which blocked `app.js` on `localhost:8000` too, and Alpine then resolved a `close()` call to `window.close` and closed the tab.
- **Timezone:** `config('app.timezone')` is `Asia/Phnom_Penh` (UTC+7, no DST) — not UTC. Every core Attendance rule is a local-time rule (`work_date`'s calendar-day boundary, `in_progress`'s "has end_time passed", the 18h overnight pairing window), and `now()`/`today()`/bare `Carbon::parse()` calls all resolve against this automatically since Laravel sets PHP's default timezone from it at bootstrap — nothing in app code references it directly. **MySQL's own session timezone is a separate setting and currently resolves to `SYSTEM`** (the Docker container's OS timezone, itself UTC) — checked deliberately, not assumed: no query in `DailySummaryBuilder`, `PunchIngestor`, or anywhere else in Attendance depends on it, because every date/datetime comparison (`whereDate`, `whereBetween`, `whereYear`) compares the stored column against a PHP-supplied literal parameter, never MySQL's own `NOW()`/`CURDATE()`/session clock. No connection-level `'timezone'` setting was added because there's nothing for it to fix — but if a future query ever calls a MySQL-side clock function, this stops being true and that query would need explicit handling.
- **Dev database:** `stampy`, in the `mysql` container (user `attendance` / password `secret`; host `mysql` inside the compose network, `127.0.0.1:3308` from the host). The `app` service's `environment:` block in `docker-compose.yml` sets `DB_*` as real environment variables, and **real environment variables outrank every `.env*` file** — so inside the container `.env`'s `127.0.0.1` / `root` values are ignored (they only describe a host-native MySQL this project no longer uses). `docker compose exec app php artisan migrate:fresh --seed` therefore wipes the dev database `stampy`, not a scratch one.
- Run `docker compose exec app php artisan migrate:fresh --seed` to reset and reseed the dev database. Seeded accounts (all password `password`, **change after first login**):
  - `admin@example.com` — admin
  - `aye.aye.mon@example.com` — manager (Engineering)
  - `kyaw.kyaw.naing@example.com` — employee (Engineering)
  - `zaw.zaw.htet@example.com` — manager (Operations)
  - (Su Su Hlaing and Thida Win are seeded as employee records with no login account, to exercise the "employee without a user account" case.)
- **Test database:** the suite runs against MySQL, not sqlite (see phpunit.xml's comment for why — briefly, sqlite has no enforced DATE column type and already hid one real bug). It needs a `stampy_testing` database, separate from the dev `stampy` one, granted to the same `attendance` user. `docker/mysql/init/01-create-testing-db.sql` creates and grants it automatically, but **only on a fresh `mysql_data` volume** — the official MySQL image runs `/docker-entrypoint-initdb.d/` scripts once, the first time the data directory is empty. If you already have an existing volume from before this file existed (e.g. `docker compose up` predates this change), run once by hand:
  ```
  docker compose exec mysql mysql -uroot -psecret -e "
    CREATE DATABASE IF NOT EXISTS stampy_testing CHARACTER SET utf8mb4 COLLATE utf8mb4_unicode_ci;
    GRANT ALL PRIVILEGES ON stampy_testing.* TO 'attendance'@'%';
    FLUSH PRIVILEGES;"
  ```
- **Running the tests:** `docker compose exec app php artisan test` (the whole suite takes seconds, not minutes) or `... php artisan test --filter=SomeTest`. Tests cannot run on the host: `phpunit.xml` pins `DB_HOST=mysql`, which only resolves inside the compose network.
- **Pre-commit hook: every commit runs the suite.** `.githooks/pre-commit` (committed) runs `php artisan test --compact` in the `app` container and blocks the commit if anything fails, or if the container isn't running — the tests can't run anywhere else (see above), so a stopped stack blocks rather than skips. It is installed per clone by `composer hooks`, which `composer install` also runs (`post-install-cmd`): it sets git's `core.hooksPath` to `.githooks`, and works from the host or inside the container, since both have git and share `.git/config` through the bind mount. On a clone that predates the hook, run `composer hooks` once. A commit takes the suite's ~55s; don't commit while another suite run is going (see "One suite at a time" below). `git commit --no-verify` is for emergencies only, never for a red suite. This exists because a test-and-commit chain once committed on a red suite when its own failure check misfired; the hook doesn't depend on whoever is committing to check.
- **Test-database safety (three layers — don't remove any):**
  1. `phpunit.xml` forces `DB_DATABASE=stampy_testing` (`force="true"`; `tests/bootstrap.php` also unsets the container's `$_SERVER` copies so the forced values reach Laravel). PHPUnit's forced values are real environment variables, so **they win over `.env.testing`** for test runs; the two files hold identical values, so they cannot disagree today — if one is changed, change both.
  2. `.env.testing` (committed; contains nothing secret) makes `--env=testing` on an artisan command actually select `stampy_testing`: `docker compose exec app php artisan migrate:fresh --env=testing`. This does not work by itself — the container's real `DB_*` variables would still win — so `bootstrap/app.php` drops them when `--env=testing` is on the command line. Without the flag, artisan still targets the dev `stampy` database, unchanged.
  3. `Tests\TestCase::createApplication()` throws before `RefreshDatabase` can wipe anything if the configured **or** live (`select database()`) database name doesn't end in `_testing`. A run pointed at `stampy` fails every test with "Refusing to run tests".
- **One suite at a time.** `stampy_testing` is a single shared database and `RefreshDatabase` runs `migrate:fresh` on it at the start of every PHPUnit process. Two concurrent runs (or anything else — a seeder, a second agent — writing to it) fail wholesale (`Table 'users' already exists`, nearly every test red) or subtly (a committed seeder row such as the `Software Engineer` position collides with tests that create that same name → `positions_name_unique`). Serial runs are deterministic — checked by running the suite repeatedly in a fixed order, in random order (`php vendor/bin/phpunit --order-by=random --random-order-seed=N`), and with the clock pinned at 21 instants: **`scripts/pinned-instants.sh`** (from the host, Compose up; extra arguments go to PHPUnit, e.g. `--filter SomeTest`) runs the suite once per instant, refuses to start while a phpunit process is already running in the container, prints one result line per instant, exits 1 if any failed, and keeps **each instant's full output in `storage/app/pinned-runs/<timestamp>/<instant>.log`** (gitignored) — so a failure that won't reproduce still leaves its error text (one at 4 Feb 08:11 didn't, before the logs existed). It works through `Tests\TestCase::setUp()`, which travels to `PIN_NOW` when that's set and does nothing otherwise (Phase 3e; the hook used to be added by hand for each check). A pinned run says so once, on stderr, before any test (`Clock pinned: every test starts at … (PIN_NOW).`, from `tests/bootstrap.php`), so a stray `PIN_NOW` in a shell or CI can't pin a run silently; an unpinned run prints nothing. About 20 minutes (the suite takes ~55s an instant); don't commit while it runs, since the hook runs the suite too. The instants: every weekday of 2–8 Feb 2026, times either side of midnight and of the 08:00–17:00 shift (00:00:30, 07:59, 08:11, 16:59:59, 17:00:01, 23:59:30), month and year boundaries (28 Feb/1 Mar, 31 Mar/1 Apr, 31 Dec 2026/1 Jan 2027 — 1 Jan both before and just after `leave:grant`'s 00:05 run, which `LeaveGrantAtAnyInstantTest` exercises at whatever instant is pinned), a leap day (29 Feb 2028, 1 Mar 2028), and mid-year 2026 and 2030. **Current state (6 Oct 2026, after Phase 3f): all 21 pass.** An earlier note claimed the same, but it had drifted: 37 tests failed at the early-2026 instants and 4 from 2027 on, because they used fixed Feb–Mar 2026 dates and only passed while the real clock was later in 2026. **The rule that keeps it passing: a test that uses fixed dates fixes its own clock** — `DailySummaryBuilderTest`, `ManualPunchTest`, `HolidayAttendanceTest` and `AttendanceBuildDailyCommandTest` pin it for the whole class in `setUp()`, and a few tests in other classes pin it themselves (`travelTo('2026-04-15 12:00:00')`, after all their data and inside 2026, so `DisplayDate` omits the year); a test relative to `today()` doesn't pin. Repeat the check after touching date-dependent code — Phase 3's leave balances depend on year boundaries. **Stopping a host command doesn't stop a phpunit process already running inside the container** (`docker compose exec` passes no signal through when the host side is killed, e.g. by a tool timeout): the orphan keeps running against `stampy_testing`, and every re-run then shares the database with it and crawls or fails — found during 3a's follow-up, where one pinned instant seemed to hang for 30 minutes and passed in 32 seconds once the orphans were gone. Before re-running, check: `docker compose exec app ps aux | grep phpunit`.

## Design system

One primary color, one accent color, one font, a small set of reusable Blade components — with full light/dark support. Apply these everywhere — don't introduce one-off styles. This look (evergreen/mint palette, sidebar + topbar shell, dark mode) was deliberately aligned with a reference UI prototype (`employee-attendance-system-2`, a Next.js/shadcn mockup called "Northstar") that is **not** part of this codebase's stack — it was used only as a visual reference, then re-implemented natively in Blade/Tailwind.

- **Font:** Inter for interface copy, loaded via Bunny Fonts (`fonts.bunny.net`) — set as the Tailwind `sans` default in `tailwind.config.js`. DM Serif Display (also via Bunny Fonts) is used as a single editorial accent — currently only the italicized word in the auth hero headline (`font-serif` utility) — never for body or UI copy.
- **Primary color:** deep evergreen, defined as the `primary` color scale in `tailwind.config.js` (50–900). Use `primary-600`/`primary-700` for buttons/links, `primary-50`/`primary-100` for tints and active-state backgrounds.
- **Accent color:** mint, defined as the `accent` color scale (50–900). Used for icon badges, the brand mark, and highlight text (e.g. the auth hero) — not for primary actions.
- **Neutrals:** the `slate` scale name is kept for continuity, but it is not Tailwind's slate: it is a CSS-variable scale (`resources/css/app.css`, read by `tailwind.config.js`) that is **warm stone in light mode** — matching the warm cream/oklch neutrals in the Northstar reference — and a **neutral, slightly cool zinc in dark mode**, where stone's red-orange cast read as brown. `dark:` classes name a step; the theme picks the hue. Never hard-code a neutral hex: read `--slate-N`. **Readable muted text is `text-slate-500` on a light card and `text-slate-600` on the light page background or a tinted fill, `dark:text-slate-400` everywhere** (4.80:1 / 6.99:1 / 5.81:1); light `slate-400` is for decorative icons only, and the AM/PM suffix takes these colours rather than an opacity — see `docs/DESIGN_SYSTEM.md`, Muted text rule. `slate-100` page background / `slate-900` in dark mode, `white`/`slate-800` cards (dark overlays and controls `slate-750`, one step above the card — the full ladder is in `docs/DESIGN_SYSTEM.md`, Dark surfaces), glass sidebar/topbar (see below).
- **Surface architecture:** glass is reserved for application-level shell surfaces: the sidebar, topbar, and authentication shell. The modal backdrop may use transparency and blur as an overlay treatment. Content surfaces are always solid: cards, tables, form controls, dropdowns, popovers, modal panels, and information panels. The `.bg-shell` utility (`resources/css/app.css`) provides the shell's subtle mint/evergreen radial backdrop in light mode; dark mode has no glow, so its neutral surfaces stay clean. See `docs/DESIGN_SYSTEM.md` for the complete v1 rules.
- **Dark mode:** class-based (`darkMode: 'class'` in `tailwind.config.js`), toggled by adding/removing `.dark` on `<html>`. A small inline script in each layout's `<head>` (`app.blade.php`, `guest.blade.php`) applies the stored `localStorage.theme` (or system preference) before paint to avoid a flash of the wrong theme. The toggle button in the topbar and on the auth pages flips the class and persists the choice. Every new component must carry a `dark:` variant — check contrast for text, borders, inputs, and hover states, not just backgrounds.
- **Radius hierarchy:** badges and compact statuses use `rounded-md`; controls and buttons use `rounded-lg`; cards, dropdowns and popovers use `rounded-xl`; modal and large overlay panels use `rounded-2xl`. `rounded-full` is for truly circular geometry such as avatars, dots and progress tracks, not badges or controls.
- **Cards:** `bg-white rounded-xl shadow-sm ring-1 ring-slate-border dark:bg-slate-800` (see `x-card`; the ring is the `border` line token, because a shadow can't separate a card from a dark page) — solid content surfaces with quiet boundaries and no decorative hover treatment.
- **Tables:** row dividers are an inset `h-px bg-slate-divider` line (the `divider` line token — every neutral line is `divider` or `border`, see `docs/DESIGN_SYSTEM.md`, Lines), not a `divide-y` utility — for a real `<table>` (e.g. Employees, Attendance), give the header `<tr>` and every body `<tr>` `relative`, then drop a `pointer-events-none absolute inset-x-6 bottom-0 h-px bg-slate-divider` span into the *last* `<th>`/`<td>` of each row (`@unless ($loop->last)` on body rows, so the final row doesn't get a trailing line before the card edge/pagination) — or, in a table with pinned trailing columns (Employees and Daily Attendance, 640–1279px; see `docs/ATTENDANCE_UI.md`), into the *first* cell with `z-[2]`, since a sticky last cell would become the span's containing block and the line must run above the pinned cells; for a card-style row list with no `<table>` (e.g. Departments, Positions), a plain `border-t border-slate-divider` on each row (`first:border-t-0`) does the same job more simply. Either way it's the **`divider` token** (1.25:1 light, 1.27:1 dark against the card), never a numbered slate step — `slate-100` was nearly invisible against a white card, and ad-hoc values drifted apart. If a new table's borders are hard to see, check the actual color, not just whether a border class is present. `hover:bg-slate-50 dark:hover:bg-slate-750/60` rows, generous cell padding (`px-6 py-4`), uppercase `text-xs` column headers.
- **Links (data rows that navigate elsewhere):** give the link text the primary accent color at rest — `text-primary-700 dark:text-primary-400` — plus a **permanent, muted underline** (`underline decoration-1 underline-offset-2 decoration-primary-300 dark:decoration-primary-700`) that strengthens on hover (`hover:decoration-primary-600 dark:hover:decoration-primary-400`), and a `focus-visible:ring-2 focus-visible:ring-primary-500` on the `<a>` for keyboard users. Color alone was tried first and wasn't enough: in a table where every name in a column is a link, there's no unlinked neighbor to contrast against, so a color-only treatment just reads as that column's styling rather than as interactivity — the underline is what actually reads as "clickable" regardless of neighboring rows. Never rely on a hover-only change (no underline until hover, color-only hover, etc.) — touch devices have no hover state, so whatever signals "link" must already be visible at rest. When a row has a separate record-level destination in addition to its name link, a trailing `chevron-right` must be visible at rest and strengthen on row hover; do not add one when the name is intentionally the sole detail-navigation affordance. Cell links keep the rest of the row selectable, which is the pattern Employees uses; the Attendance tables instead keep the employee name as plain text and make the trailing chevron (visible at rest, 40px, `aria-label` "View attendance for {name}, {date}") the row's only link — see `docs/ATTENDANCE_UI.md`; making a whole row clickable remains valid only when it has no competing actions or selectable operational data. In every case, a link that looks like plain text, or blends into its column, is in practice no link.
- **No interactive element is ever hover-only, full stop — this is the general rule the Links bullet above is one instance of.** Touch devices have no hover state, so whatever signals "this is interactive" and whatever makes it *reachable* must both already be true at rest: not just a link's underline/chevron, but a row's edit/delete icon buttons, an inline "make default" action, any control whose only path to visible or clickable was `opacity-0 … group-hover:opacity-100`. That exact pattern was the default on every list's row actions — Departments, Positions, Holidays, Schedules (edit/delete, and Schedules' "Make default"), the Employees directory table (edit/deactivate/reactivate), and the employee profile's schedule-history delete button — until a manual pass confirmed none of them were reachable at a mobile/touch width and it was removed from all six; the buttons still darken/tint on `hover:bg-*`/`hover:text-*` same as before, that part was never the problem. `group-focus-within:opacity-100` (present on five of the six) looked like it covered keyboard users, but keyboard-focus-only isn't touch-reachable either — it's not a substitute for at-rest visibility, only an addition to it. When adding a new row action, start visible; hover/focus may still *strengthen* the existing look (a background tint, a color shift) but must never be the only way to reveal or reach it.
- **Status vs. timing — two independent dimensions, never conflated:** `AttendanceStatus` answers exactly one question, "did they attend" — `present` / `incomplete` / `absent` / `off` / `holiday` / `leave` / `in_progress`. Whether the *timing* was off (arrived late, left early) is a completely separate fact, tracked on `DailyAttendance`'s `late_minutes`/`early_leave_minutes` columns and surfaced through `isLate()` / `leftEarly()` / `hasTimingException()` — **never** as a status value, and (since Design System v1.1) **never as a colour bucket either**. A `Late` status used to exist and was removed: it mixed the two dimensions, and a day that was both late *and* left early would have needed a third, combined status — the question "what do we call a day that's both?" was itself the sign timing didn't belong in the enum. A `timing` display variant (an amber "Present") was removed in v1.1 for exactly the same reason one level up: one cell colour was carrying two facts. **Principle: a cell or badge colour encodes the attendance STATUS only — one value per day. Attributes that can co-occur on the same day (timing exceptions now, partial leave later) are annotations inside the cell, never the cell/badge colour.** A day both punches cover is always `present`, whatever the timing; a late in-punch on a day that is still `in_progress` or ends `incomplete` keeps that status too (Phase 2.6) — the late annotation rides along, the status and colour don't change. On a holiday every status's timing is forced to 0 by the builder (see the Database schema section's precedence order), so it can never carry a timing annotation.
- **`DailyAttendance::displayVariant()` is the single source of truth for colour** — the one method that maps a day's status to its display bucket, **status-only** (a late Present day is `present`, green). Every view (calendar, table, list) colours a cell/badge by looking up this variant; no view may re-derive a colour bucket by checking `late_minutes`/`early_leave_minutes`/`status` directly. This is what keeps the three views from drifting apart the way they did when each independently decided "does this day have a problem":

  | variant | colour | meaning |
  |---|---|---|
  | `present` | green | normal day |
  | `incomplete` | violet | data defect — a punch is missing |
  | `absent` | red | did not attend |
  | `off` | slate | not a working day |
  | `leave` | accent (mint) | approved leave (Phase 3) — must never read as `off`: a day that used someone's leave balance is not a weekend |
  | `in_progress` | blue | the day is still open and would otherwise be absent/incomplete — an in-only day until first in-punch + 18h (Phase 2.7: past the schedule end and past midnight), a punchless or out-only day today until the schedule end — "not yet", not a failure |
  | `holiday` | fuchsia | a company holiday (see Database schema) |
  | not calculated | muted | no `daily_attendances` row yet — not a variant string (there's no model instance to call it on), handled separately in each view |

  `violet` (`incomplete`) was a deliberate, one-time exception to the app's core green/amber/red/slate palette (plus primary/accent for a couple of low-frequency states) — Incomplete (a device defect — a punch never recorded) and a timing exception (normal employee behavior) used to share amber and were indistinguishable at a glance in light mode. Amber is now reserved for the timing *annotation* (below), which is exactly why Incomplete must not drift back to it. `blue` (`in_progress`) and `fuchsia` (`holiday`) followed for the same reason when Phase 2.4f added both: `in_progress` must not read as red or amber (it means "not yet", not a problem), and `holiday` deliberately avoids primary/accent — both are still green-family hues under this app's palette, which would repeat the exact amber/violet confusability this section already fixed once. Together with `accent` (below) these are the four colors `x-badge` carries beyond its base five (`primary`/`green`/`red`/`amber`/`slate`) — `violet`, `blue`, `fuchsia` and `accent`, nine in all. The `accent` **`x-badge` variant** exists only for `leave` (the accent colour itself is used more widely — the brand mark, icon badges and highlight text, see the Accent bullet above): `text-accent-700 dark:text-accent-300` measured 5.05:1 (light, on `bg-accent-50`) and 8.59:1 (dark, on the badge's `bg-accent-900/30` composited over the card; 8.92:1 on the calendar cell's `/20`), by the same method that reproduces the violet/blue figures above. Don't add another one-off hue for a future variant without the same kind of justification, and don't "clean this up" back to a base color. `text-violet-700 dark:text-violet-300` (light: 6.48:1 on `bg-violet-50`; dark: 7.65:1 on the badge's `bg-violet-900/30` composited over the card, 7.83:1 on the calendar cell's `bg-violet-900/20`), `text-blue-700 dark:text-blue-300` (6.16:1 / 7.56:1 badge, 7.81:1 cell), `text-fuchsia-700 dark:text-fuchsia-300` (5.89:1 / 7.89:1 badge, 8.13:1 cell) — the `-300` in dark mode for all three, not `-400`, for the same reason `absent` uses `red-300`: measured against the actual composited background, not assumed from the shade number.
- **The calendar's status icon and cell fill reflect attendance, not timing — and fill emphasizes exceptions:** a late or early Present day is an ordinary `present` cell with `present`'s check icon — the icon answers "did they show up" (shape-safe in greyscale on its own), while the amber marked time (below) carries the timing exception. A Present cell uses the neutral card surface (no green fill); the green day number and check carry the status, and tinted fills are reserved for the exception statuses (absent, incomplete, leave, holiday, in progress). Off cells are the quietest in the grid: no fill, a medium-weight `slate-500` number, a fainter icon and a dashed boundary. This is presentation only — `displayVariant()` is unchanged and table badges / the day modal's pill stay green. Today is a filled circle behind the day number — the shared filled selected state: white semibold on `primary-600`, dark white on `primary-500` (4.57:1 text, 3.26:1 fill against the dark card) plus `aria-current="date"`, not a cell border — in the calendar only: in the date picker a fill means a chosen date, so today there is a quiet marker (see `docs/ATTENDANCE_UI.md`, Date picker). In-cell times are ≥12px with a ≥10px AM/PM. Conflating "attended" and "arrived late" into one icon (a clock), and later into one amber cell colour, were both earlier, now-removed designs.
- **Marked times and timing values (a specific value is out of range, not just the day):** the timing fact is marked on the value that carries it, in the **timing text** colour — `amber-700` in light mode, `amber-300` in dark mode (`yellow-700` was tried and rejected as muddy; amber only read reddish against the old green-50 Present fill) — **never with an underline — underline is reserved for links everywhere**. In the calendar and the day-detail modal the late In / early Out time is rendered with `<x-time marked>` (`font-medium text-amber-700 dark:text-amber-300`), with an `aria-label` such as "Arrived 16 minutes late"; the medium weight is the non-colour cue alongside the amber, and no extra "+80m" label goes in calendar cells. In tables (the Daily Attendance list and the per-employee table view) In/Out times stay neutral and the **Late / Early values themselves** are amber with the same weight — the column position plus the value-vs-em-dash already make them readable without colour. Measured: `amber-700` is 5.02:1 on white (cards, Present calendar cells) and 4.81:1 on the `slate-50` row hover; `amber-300` is 10.33:1 on the dark card and 9.38:1 on the dark row hover. Amber badges and alerts are a separate role. The red underline this replaced (v1) made a normal late arrival look like an error and borrowed the link affordance. A prior version before that used a plain corner dot; it was removed for saying too little — mark the specific value, not the day.

**Alpine note:** any element using a bare `@click`/`x-show`/etc. with no `x-data` anywhere in its ancestor chain silently gets no directive binding at all (confirmed empirically on this Alpine 3.17 setup — it isn't just an edge case). Add `x-data="{}"` directly on any standalone interactive element that isn't already nested inside a component with its own `x-data` (e.g. the dark-mode toggle buttons).

**Blade gotcha: never embed a `@if`/`@endif` (or any other directive) directly inside a self-closing `<x-component ... />` tag's attribute list.** Blade's component-tag compiler (`ComponentTagCompiler::compileSelfClosingTags()`) matches the tag with a regex that only recognizes a fixed set of attribute token shapes — `word="value"`, `:$var`, `@class(...)`, `@style(...)`, `{{ $attributes }}` — and nothing else; a raw `@if (...) autofocus @endif` spliced between attributes doesn't match any of them, so the *entire tag* silently fails to compile as a component and is emitted as literal, uncompiled text instead. No error, no warning — a browser just renders it as an unrecognized custom element and drops the attribute text, so the component appears to vanish. This is exactly what made the profile page's email `<x-text-input>` disappear (it had `@if ($user->employee) autofocus @endif` inline in its attributes). Branch outside the tag instead — two full `<x-component>` calls inside an `@if`/`@else`, the way the Name field right above that same input already did — never a directive inside one tag's attribute list.

**Modals:** every create/edit modal builds on `<x-modal>` (`resources/views/components/modal.blade.php`) — never hand-roll the overlay/backdrop/focus-trap again. `entangle="propertyName"` two-way binds the modal's Alpine `show` state to a Livewire boolean via `$wire.entangle().live`, so Escape and backdrop-click correctly close the Livewire property itself instead of only hiding the panel client-side. Modal panels are always solid and `rounded-2xl`; there is no surface prop. `<x-confirm-dialog>` teleports to `<body>` too, at `z-[60]` — one layer above modals, since a confirmation opened from inside a modal (the day modal's Void) must sit on top of it; at the shared `z-50` the modal, teleported later, covered it. While open it catches Escape on `window` in the capture phase and stops it, so Escape closes the confirmation and not the modal underneath. The shared panel intentionally has no `overflow-hidden`: the employee form applies scrolling to its own body, while panel-level clipping would risk cutting focus rings and overlay content. `maxWidth` only accepts the named presets defined in the component (`sm`/`md`/`lg`/`xl`/`2xl`/`employee-form`) — never interpolate a raw pixel value, since Tailwind's class scanner only picks up literal text in source files and a runtime-built `max-w-[...]` string produces no CSS silently; add a new named preset instead. Focus handling is automatic and has no opt-in: opening always moves focus into the dialog (its `autofocus` field, else the first focusable element), Tab is trapped inside, and closing returns focus to the trigger — see `docs/DESIGN_SYSTEM.md`, Overlays. Never put a `//` comment inside an Alpine `x-init`: it is compiled as an expression and the comment breaks it.

**`<x-modal>` teleports to `<body>` (`<template x-teleport="body">` wrapping its root) — don't "clean this up" back to a plain div.** It guarantees viewport-relative positioning and avoids clipping or containing-block bugs when a modal is rendered within a nested component or shell treatment. `Employees\ScheduleAssignments` is intentionally supported while nested inside `<x-card>` on the employee and profile pages.
Don't swap this for Livewire's own `@teleport`/`@endteleport` either, expecting different behaviour — checked directly in `Livewire\Features\SupportTeleporting`: it compiles to exactly `<template x-teleport="...">`/`</template>`, the same markup, not a different mechanism. The Alpine morph plugin this Livewire version bundles is teleport-aware (`if (from._x_teleport && to._x_teleport) { context.patch(...) } ` in the shipped JS) — verified in a real browser, not just read in the source: typed values in a teleported modal survive an unrelated round-trip on a sibling component *and* two forced round-trips on the same component that owns the modal, a full save-and-close correctly hides the teleported clone (not just the inert original), and five open→save→reopen cycles left exactly one modal instance and one `#dept_name` input in the document throughout, no growth. An older, unrelated revert in this codebase (`f83aa03`, an inline table-row panel, not a modal) cited morph-unreliability as a secondary reason not to bother — its own comment says the actual bug there was something else entirely, and that citation was never itself empirically isolated the way this one now has been. Don't re-raise it without re-testing it.

## Naming conventions

- **Tables/migrations:** snake_case, plural table names, one migration file per table, named `create_{table}_table`. **The interim exception that used to live here is over (Phase 2.5c).** Through Phase 2's testing and bug-fixing, schema changes landed as separate alter-table migrations (`add_*`, `remove_*`) instead, specifically so they'd be picked up by databases that had already run the original `create_{table}_table`; the plan from the start was to fold them back in once that phase ended, and Phase 2.5c did exactly that — five alter-migrations (`add_status_index_to_employees_table`, `remove_deleted_at_from_employees_table`, `add_unique_index_to_department_and_position_names`, `add_voided_at_punched_at_index_to_attendance_logs_table`, `remove_work_schedule_id_from_employees_table`) folded back into `create_employees_table`/`create_departments_table`/`create_positions_table`/`create_attendance_logs_table`, each ending up with the exact final schema those tables already had — verified with a schema dump diff (clean apart from the deliberate `email_verified_at` removal — see Tech stack — and the `migrations` table's own row count) and a SHA-256 hash of every table's substantive data (identical) across a `migrate:fresh --seed` before and after. **From here on, every schema change is its own alter-table migration again — permanently, not another interim phase.** This wasn't just tidiness: consolidation only works because nothing was in production yet. The next schema change might land on a database with real data, where a `create_{table}_table` can't be edited after the fact — a deploy has already run it — so an alter-migration is the only form a change can safely take from now on. Don't fold anything back into a create-migration again without the same reasoning holding (i.e., don't — it won't).
- **Models:** singular StudlyCase (`Employee`, `Department`), relationships as standard Eloquent methods (`department()`, `employees()`).
- **Livewire components:** namespaced by feature under `App\Livewire\{Feature}\{Action}`, e.g. `App\Livewire\Employees\Index`, `App\Livewire\Employees\Form`. Matching views under `resources/views/livewire/{feature}/{action}.blade.php` (kebab-case). A single `Form` component handles both create and edit (mounted with an optional model for edit).
- **Policies:** `app/Policies/{Model}Policy.php`, auto-discovered by Laravel's naming convention (no manual registration needed).
- **Routes:** RESTful names (`employees.index`, `organization.index`), grouped by role-based middleware in `routes/web.php`.

## Coding conventions

- **Validation:** Livewire components validate server-side, via a `rules()` method or an inline `$this->validate([...], [messages])` (as `Attendance\Show::addPunch()` and `Holidays\Index::save()` do) — never trust unvalidated `wire:model` input. The plain controllers are Breeze's auth/profile ones plus `/password/change` (`ForcePasswordChangeController`); they validate inline with `$request->validate([...])` / `validateWithBag()`. Only `LoginRequest` and `ProfileUpdateRequest` are Form Requests, and both are Breeze scaffolding — no feature of ours uses one. Introduce a Form Request only when a plain controller of ours starts handling substantial validated input (e.g. a future API).
- **Authorization:** every Livewire component that manages a resource calls `$this->authorize(...)` in `mount()` for page-level checks and again in the specific action method (e.g. `deactivate()`, `save()`, `delete()`) before mutating. Route groups also carry `role:` middleware as a second layer of defense (see `routes/web.php`). A component that holds the record as a typed model property and has read-only actions (paging, opening a modal) must **also authorize in `render()`**, which every request ends in — `Attendance\Show`, `Employees\Show`, `Employees\ScheduleAssignments` and `Employees\StatusModal` do. Why: those actions are safe today only because Livewire's `ModelSynth` re-derives a typed model property from the signed snapshot and ignores whatever the client sends; that protection is framework behaviour, not this component's, and storing the id as a plain `int` (an ordinary-looking refactor) would silently remove it. It also stops a page opened while authorised from serving data after access is revoked (an employee moved out of a manager's team, say). This applies with no exception to a component nested inside another authorized one, too: `Employees\ScheduleAssignments` is embedded on `Employees\Show`, but it's still its own Livewire component with its own signed snapshot, and an update request aimed at it never routes through the parent's `render()` — so it authorizes in its own `mount()`, its own mutating actions, and its own `render()`, exactly like any standalone component (see the Roles & authorization section, footnote ³, for what each of those three checks).
- **Employee lifecycle:** no soft deletes anywhere — deactivating sets `employees.status = inactive` plus `left_on`, their last day (Phase 3a), and the employee row and their attendance up to `left_on` are never removed by the app. **Deactivation and reactivation happen only through `Employees\StatusModal`** — the directory's row actions and the profile header open it; the employee form has no Status field, and creating an employee always makes an active one. `Employee::booted()` enforces the period on every write (`InvalidEmploymentPeriodException`: inactive ⇔ `left_on` set, `join_date ≤ left_on ≤ today`), and `Employee::scopeActiveOn()`/`isActiveOn()` is the one definition of "employed on date D" (`join_date ≤ D` and (`left_on` null or `D ≤ left_on`)). **Attendance figures use it; lifecycle filters use `status`.** Every attendance figure that counts employees for a day — the dashboard's live strip, today's breakdown, Needs attention, the Department card (and its `N / M` headcount), the trend, `todayIsPending()` — counts the employees active on that day, the same set the builder builds for, so a future joiner is never "Not in yet" and a leaver counts up to their last day. The Employees directory's Total/Active/Inactive figures and its status filter, the employee form's manager options, and the Schedules tab's "currently assigned" counts and bulk reassignment stay on `status`: they ask where someone is in their employment lifecycle now, not who was employed on a given day. Both actions go through `App\Services\EmployeeLifecycle`, which writes first and then rebuilds from `left_on + 1` to today, the same way as `EmployeeScheduleAssigner` (a rebuild failure is a non-blocking amber warning, logged with the `attendance:build-daily … --employee=…` command that heals it). `DailySummaryBuilder::build()` removes the row for a date the employee wasn't employed on, so a backdated deactivation leaves no stale rows after `left_on`; every build (`attendance:build-daily`, an import's rebuild, a holiday's rebuild) selects employees by employment period, not by today's `status`, so a mid-day deactivation with `left_on` = today still has that day finalised. **Reactivation means "the deactivation was a mistake":** `left_on` is cleared, the gap days become ordinary days again (absent if punchless). Leave that deactivating cancelled or shortened (Phase 3c, `LeaveRequestService::applyDeactivation()`) is **not** restored — re-file it if it still applies. A real rehire — a second employment period — is not supported; that is a known limitation, not a Phase 3 item. Departments/positions with employees assigned cannot be hard-deleted either (guarded in `Departments\Index::delete()` / `Positions\Index::delete()`).
- **User/HR data split:** `users` is auth-only (name, email, password). All HR data lives on `employees`, linked via nullable `employees.user_id` — an employee may exist with no login (not yet onboarded to self-service), and a `User` always optionally has one `Employee` profile. `users.name` is the one exception to "auth-only, independently editable": for a linked user it mirrors `employees.full_name` rather than standing on its own — the name is HR data, and admins own it. The profile page shows it read-only (sourced from the employee record) and `ProfileController::update()` enforces that server-side by dropping any submitted `name` for a linked user, not just hiding the input; `Employees\FormModal::save()` is the other half, copying an admin's changed `full_name` onto the linked user in the same save so the topbar and anywhere else `users.name` appears can't drift from the HR record. An unlinked user (no `Employee` profile) still edits their own name freely.
- **Tests:** `tests/Feature` uses Livewire's `Livewire::test()` harness against components directly (mount/call/assert) for business logic, and plain HTTP tests (`$this->get(...)->assertForbidden()`) for route-level role gating, since Livewire's test harness converts `AuthorizationException` into a response rather than letting it bubble as a PHP exception.

## Testing notes

- **`EmployeeFactory`'s `join_date` is fixed at `2020-01-01`, not random — on purpose.** It used to be random over the last 3 years. Once `addPunch()` validated punch dates against `join_date`, every attendance test that adds a punch on a fixed past date (the suite uses Feb/Mar 2026 dates) failed whenever that employee's random join date happened to fall *after* the punch — about 1 in 5 per test, and with a dozen or so such tests at the time, **7 of 10 full runs failed** (1–5 different tests each time, so it looked like flakiness, not a bug), measured before the default was fixed. A test that needs a particular join date passes `join_date` explicitly; don't restore a random default.
- **Livewire authorization tests:** after a Livewire call is denied by `authorize()`, the response is a 403 rather than a normal component snapshot, so chaining further `->set()`/`->call()` on the same test instance throws `Invalid Livewire snapshot structure`. Assert `->assertForbidden()` on the denied call itself; start a fresh `Livewire::test()` instance for any subsequent assertions.
- **Every `Employee::factory()->create()` needs a default `WorkSchedule` to already exist** (Phase 2.5b) — creation now always assigns one (`Employee::booted()`), and with none, it throws instead of silently succeeding. A test that doesn't otherwise care about schedules still needs `WorkSchedule::factory()->create(['is_default' => true]);` somewhere in its `setUp()` before any employee gets created; deliberately not a global fixture in `Tests\TestCase` (this codebase seeds roles per-file the same way, not globally, and a global default would also break the one test that specifically wants zero schedules to exist, `EmployeeScheduleAssignmentTest::test_creating_an_employee_with_no_default_schedule_creates_nothing_and_throws`).
- **A `scheduleAssignments`/`scheduleOn()` result cached on an `Employee` instance goes stale the moment something *else* writes a new assignment row for that same employee** — `EmployeeScheduleAssigner::assign()` calls `$employee->unsetRelation('scheduleAssignments')` before rebuilding for exactly this reason (see the Database schema section above). The same staleness bites test code: asserting `scheduleOn()` on an `$employee` variable that was already used earlier in the test (including implicitly, e.g. by a component's own `render()` during `Livewire::test()`'s initial mount) needs `->refresh()` first, or it reads the pre-write answer. Several tests in `EmployeeScheduleAssignmentsComponentTest`/`EmployeeScheduleAssignerTest` do this deliberately — it's not defensive paranoia, it reproduces a real failure without it.
- **`DatabaseSeederTest` runs the real `DatabaseSeeder`** (`$this->seed()`, ~3s) and asserts every resulting employee has at least one schedule assignment — a regression test for the exact bug `DatabaseSeeder`'s `WithoutModelEvents` caused (see Roles & authorization's Authorization convention and the Database schema section above): it silently suppressed `Employee::booted()`'s listener, seeding 35 employees with zero assignments and no error anywhere. Confirmed to actually catch it (not just superficially): temporarily reintroducing the trait fails this test, listing all 35 employees by code. If this test ever needs `WorkSchedule::factory()` or similar test setup added ahead of it, that's a sign something *else* now also depends on seed order — don't just silence the assertion.
- **A seeder that needs reproducible randomness draws from its own engine** (`new Randomizer(new Mt19937($seed))`, as `AttendanceLogSeeder` does), **never PHP's global `mt_rand()`/`array_rand()` state**, and decides nothing by a database id. Both once made the seed differ inside the suite from a standalone run (Phase 3f): rolled-back inserts advance AUTO_INCREMENT, and `Faker\Generator::__destruct()` reseeds the global generator at random whenever an old generator is garbage-collected. `DatabaseSeederTest`'s seed-twice pair checks both.
- **Factory defaults that keep the Phase 3a invariants out of the way** (both deliberate): `EmployeeFactory` gives an `['status' => 'inactive']` employee `left_on = join_date` — valid, and outside every recent date, so they behave like the "gone" employees older tests meant; use `->inactive('Y-m-d')` for a real last day. `WorkScheduleFactory` leaves `break_start` null, because a default of 12:00 would fail break_start's own rule on any test schedule with other hours or no break; use `->withBreakStart()` when a test needs one.
- **`php artisan make:seeder` generates a class with `use WithoutModelEvents;` by default.** That trait is exactly what caused the bug `DatabaseSeederTest` (above) now guards against — any *new* seeder that creates `Employee` rows and keeps the generated trait will silently skip `Employee::booted()`'s auto-assignment listener the same way, and `DatabaseSeederTest` only covers `DatabaseSeeder` itself, not a seeder added later. Delete the `use WithoutModelEvents;` line (and its `use Illuminate\Database\Console\Seeds\WithoutModelEvents;` import) from any new seeder that touches `employees`, or write that seeder's own regression test the way `DatabaseSeederTest` does.

| break_start | time, nullable | Phase 3a, alter-migration: when the break begins — the morning/afternoon boundary for half-day leave (AM = `start_time`–`break_start`, PM = `break_start + break_minutes`–`end_time`). Needs `break_minutes > 0` and must fit inside the shift. Locked once referenced, except that a locked schedule may go from null to a value once (below). Read only on a half-day leave day (`ExpectedWindow`, Phase 3d) |
| workdays | json | array of ISO weekday numbers (1=Monday); at least one required. Locked once referenced |
| is_default | bool | default `false`; the schedule a **newly created** employee is assigned to (`Employee::booted()`) — it no longer affects any existing employee's history the way a "no row → current default" fallback once would have (Phase 2.5b's whole reason for existing, see below) |

**Locking, defaults, and validation — all enforced on the model (`WorkSchedule::booted()`), not just the admin form:**
- **Locked once referenced.** Once any `employee_work_schedules` row or `daily_attendances` row references a schedule, `start_time`/`end_time`/`grace_minutes`/`break_minutes`/`break_start`/`workdays` can never change (`WorkScheduleLockedException`) — `DailySummaryBuilder` must always be able to recompute an already-built row identically, which a schedule that keeps changing underneath it would break. To change hours: create a new schedule and reassign the affected employees (`EmployeeScheduleAssigner`, below) — never edit a locked one, even via `tinker`.
- **One exception: `break_start` may go from null to a value once, even on a locked schedule** (Phase 3a; `WorkSchedule::lockedFieldsChanged()`). It is the morning/afternoon boundary for half-day leave and is read only on a half-day leave day, and a half-day request on a schedule without it is refused (Phase 3 scope, rule 19) — so no built row can depend on it having been null, and setting it can't change one. Changing or clearing a value once set throws like any other locked field. The Schedules form shows "Break starts" editable while the schedule is unlocked or the value is still empty, and read-only otherwise. The migration that added the column backfilled `12:00` on every schedule whose break fits there, through the query builder (the model's lock would refuse it); that was safe only because nothing read the column yet.
- **Once configured, exactly one default remains.** A fresh install may temporarily have no schedules/default while it is being configured, and employee creation fails clearly in that state. Once a default exists, setting `is_default` on another schedule unsets the previous one in the same transaction (`WorkSchedule::save()` wraps every save). The current default can't be deleted or unset directly (`WorkScheduleIsDefaultException`) — either would leave new-employee creation with nothing to assign.
- **Can't delete a referenced schedule** (`WorkScheduleInUseException`) — the same "referenced" test as locking, above.
- **Shape validation** (`InvalidWorkScheduleException`): `end_time` after `start_time`, at least one workday, `break_minutes` shorter than the shift; a `break_start` needs `break_minutes > 0`, and `start_time < break_start` and `break_start + break_minutes ≤ end_time`.

**Minute arithmetic truncates, never rounds** — `late_minutes` and `early_leave_minutes` are `intdiv(seconds, 60)` in `DailySummaryBuilder::calculate()`. Concretely, against an 08:00 start with 10 minutes' grace: `08:10:59` is **not** late (grace is inclusive through the whole of minute 10), late begins at `08:11:00`, and `08:11:59` is 11 minutes late, not 12; likewise leaving at `16:59:01` is not an early leave. **This is a deliberate rule, not an oversight — do not "fix" it to `round()` or `ceil()`.** Wherever rounding is ambiguous, attendance favours the employee: docking someone over seconds is indefensible, especially once these minutes feed payroll. `round()` looks more accurate in isolation, and would quietly start marking arrivals from `08:10:30` onward as late. Pinned by `DailySummaryBuilderTest::test_seconds_never_count_against_the_employee_late_and_early_minutes_truncate` (and the grace boundary itself, `>` not `>=`, by `test_arrival_exactly_at_the_end_of_grace_is_not_late`).

**`employee_work_schedules`** (Phase 2.5b) — one row per schedule *change*: the named schedule applies to that employee from `effective_from` until their next row's `effective_from`, or forever if it's their latest. Replaces a single `employees.work_schedule_id` column (removed), which recorded only an employee's *current* schedule — reassigning someone, or editing a schedule's hours, used to silently rewrite already-built history the next time it ran, because `DailySummaryBuilder` always resolved "whichever schedule they're on today," not "whichever schedule was in force on the day being built."

Unique on `(employee_id, effective_from)`. **No `effective_to` column, deliberately** — storing an end date makes overlaps and gaps possible; deriving it (below) makes both impossible.

**`Employee::scheduleOn(CarbonInterface $date): WorkSchedule`** is the one place this is resolved: the employee's *latest* assignment with `effective_from <= $date`, or their *earliest* one if `$date` precedes every assignment (e.g. `join_date` was edited to something earlier after the fact — every date from `join_date` onward must resolve to *something*). Every place that used to call the now-removed `Employee::effectiveSchedule()` calls this instead, passing the date actually being built — not `today()`. Accessing this (or the underlying `scheduleAssignments()` relation) queries once per `Employee` instance and is cached on it for the rest of the request, so a build run that reuses one `Employee` across many dates (`attendance:build-daily`, `rebuildAround()`/`rebuildFrom()`) only pays for it once — the same memoization pattern as `subordinateIds()`.

**Every employee always has at least one assignment — never a "no row → current default" fallback.** `Employee::booted()`'s `created` listener assigns the current default schedule, effective from `join_date`, in the same transaction as the employee insert itself (`Employee::save()` wraps every *new* row's save in `DB::transaction()`) — a missing default leaves neither row behind, and throws `NoDefaultWorkScheduleException` (the same exception `effectiveSchedule()` used to throw at build time; it's now only reachable at employee-creation time). Existing employees are backfilled the same way, once, by the migration that introduces the table (`App\Support\EmployeeScheduleBackfill`, kept as its own class so the backfill rule is directly testable without exercising the migration file). `NoScheduleAssignmentException` is the separate, should-never-happen case of an employee with zero assignment rows — a data-integrity bug, not a missing-default one. `attendance:import` catches it around its rebuild the same way it used to catch `NoDefaultWorkScheduleException`. `attendance:build-daily` catches it **per employee**, not around the whole run: one employee with no assignment is skipped (not built for any date in the range) and named in the summary, but every other employee in the run still gets built — a single broken employee shouldn't hide whether the other 34 are fine. Still exits non-zero, and still names every affected employee, not just the first.

**`App\Services\Attendance\EmployeeScheduleAssigner`** is the one place an assignment is created or changed outside of that automatic default — the employee profile's per-employee assignment (`Employees\ScheduleAssignments`) and the Schedules tab's bulk reassignment both go through it. `assign()` upserts on `(employee_id, effective_from)` (reassigning at a date that already has a row replaces it, rather than colliding) and always follows with `DailySummaryBuilder::rebuildFrom($employee, $effectiveFrom)` — from the effective date through today, clamped to `join_date` the same way `rebuildAround()` clamps its own D-1/D+1 window (both share a `buildRange()` helper for the actual day-by-day loop). A future-dated assignment rebuilds nothing. `bulkReassign()` moves every **active** employee currently on schedule A (per `scheduleOn(today())`, the same resolution the builder itself uses — not a separate SQL approximation that could drift from it) to schedule B. **A subtlety worth knowing if you touch this again:** `Employee::scheduleAssignments()` caches after first access (see above) — `bulkReassign()`'s own filter step (`scheduleOn(today())` on every candidate) primes that cache on each instance *before* the assignment write, so the write loop explicitly drops it (`unsetRelation('scheduleAssignments')`) before rebuilding; skipping that step silently rebuilds against the *old* schedule.

**The write and the rebuild are two separate steps, in that order, everywhere in this class.** Every assignment row is always safe to write — a single row for `assign()`, or every row for a bulk move, written together in one `DB::transaction()` — while the rebuild that follows can legitimately fail partway (a deploy restart, a DB hiccup, any exception) without corrupting anything, because `daily_attendances` is derived and always recomputable (see above). A rebuild failure is never allowed to roll back or block the assignment write; it's reported (returned as `rebuildError` in the method's array result, e.g. `['days' => int, 'rebuildError' => ?string]` for `assign()`, plus `['employees' => int, ...]` for `bulkReassign()`), logged (`Log::error`), and named with the exact `attendance:build-daily --from=… --to=…` command to heal it, since re-running the same assign/bulk-reassign action is *not* the fix — see the next paragraph for why. `Employees\ScheduleAssignments::assign()` and `::deleteAssignment()` surface `rebuildError` the same way, as a non-blocking amber warning (`addError('rebuild', …)`) rather than a failure, since whatever it names (the assignment change, or the row deletion) already succeeded.

**`bulkReassign()` is capped at `EmployeeScheduleAssigner::MAX_BULK_LOOKBACK_DAYS` (60) days back**, enforced both here and, redundantly, as an inline Livewire validation rule on `Schedules\Index::bulkReassign()` (`BulkReassignmentTooFarBackException` if bypassed) — a bulk move's cost is employees × days rebuilt, unlike a single `assign()`, which has no such cap (rebuilding one employee over a year is still well under a second). Measured on the `stampy_testing` database at realistic scale: 200 employees 60 days back took ~15s; 200 employees 365 days back took ~88s, past nginx's default 60s `fastcgi_read_timeout` in this app's own docker-compose stack, with no PHP-side execution-time limit to stop it running and no `ignore_user_abort()`, so the request is simply cut off mid-work once nginx gives up — the cap exists so that's found here, not by a slow production request. **Why every assignment is written before any rebuild starts, specifically for the bulk case:** if writes and rebuilds were interleaved per employee and something failed partway (some employees moved, some not), retrying the same bulk move wouldn't heal it — the already-moved employees no longer match "currently on schedule A" and wouldn't be selected a second time, so the one whose rebuild was cut off would never be reached again. Writing every assignment first makes the operation retry-safe for that half unconditionally; only the rebuild can still fail, and *that's* healed by running the named `attendance:build-daily` command over the stated range (idempotent, safe to re-run), never by calling `bulkReassign()` again. With a 60-day cap, the stale window a failed rebuild can leave can reach 60 days — well past the nightly scheduled rebuild's own 7-day healing window (see "`daily_attendances` builds itself" below) — so it's surfaced and logged rather than left to heal itself.

**Known, accepted limitation: the on-screen `rebuild` warning is a one-shot Livewire validation error, not a durable notice — it disappears after the very next Livewire round-trip, not just on navigation.** `Employees\ScheduleAssignments::assign()`/`::deleteAssignment()` surface `rebuildError` via `addError('rebuild', …)`, which Livewire's error bag only carries in the response for the request that set it; confirmed empirically (not assumed): a test that forces the failure, asserts the error is present, then performs one *unrelated* `set()` on the same component instance — nothing to do with validation — finds the error gone. So if the admin doesn't read the amber banner in that exact instant (closes the modal and immediately does anything else that fires a Livewire request — scrolls past a lazy-loaded section, another component's poll, an unrelated click), it vanishes with no trace in the UI. This is safe, not silent data corruption: the assignment write always lands first and is never rolled back (see above), so only `daily_attendances` can be stale, and the durable record is the `Log::error()` line, not the UI banner:
  - `assign()`: `"Schedule assignment for {employee_code}: rebuild failed partway ({exception message}). Not every affected day may have been rebuilt. Run: php artisan attendance:build-daily --from={effective_from} --to={today} --employee={employee_code}"`
  - `bulkReassign()`: `"Bulk schedule reassignment: rebuild failed partway, after all {N} assignment(s) were already written ({exception message}). Not every affected day may have been rebuilt. Run: php artisan attendance:build-daily --from={effective_from} --to={today}"`
  - `deleteAssignment()`: same shape as `assign()`, `"Schedule assignment deletion for {employee_code}: rebuild failed partway (…). …"`

  Grep the log for `rebuild failed partway` and run the `attendance:build-daily` command it names — that's the fix regardless of whether anyone saw the banner. Note the nightly scheduled rebuild only heals the last 7 days (see "`daily_attendances` builds itself" below), so a failure older than that stays stale until someone runs the command by hand. If rebuild failures turn out to happen in practice (not just in tests), revisit this with a state-driven approach instead of a one-shot flash: record the failed range somewhere durable, retry it from the scheduled task, and show a banner that stays up until it's actually healed rather than until the next click.

Unique on `(employee_id, punched_at, source)` — deliberately *not* including `voided_at`: on MySQL a unique index treats every `NULL` as distinct from every other `NULL`, so including it would let the same device punch collide, get voided, and then be re-imported as a live "duplicate" — reopening the exact bug the index exists to prevent (confirmed empirically, not assumed). Also a plain, **non-unique** index on `(voided_at, punched_at)` (`attendance_logs_voided_at_punched_at_index`). Measured at 208,800 punches (200 employees × ~2 years): `type: ALL` becomes `type: ref` with a backward index scan and no filesort, ~66 ms down to ~0.11 ms. Don't drop it as redundant with the unique index; it isn't.

**Punches and builds can't reach outside real time.** `Attendance\Show::addPunch()` rejects a punch dated outside the employee's employment period (before `join_date`, or after `left_on` — the message names the period), dated after today, or timed later than the current time today (exactly "now" is allowed), each with a message naming the constraint. `attendance:build-daily` rejects any `--date`/`--from`/`--to` after today with an error and exit code 1 — it never silently clamps the range, so an operator who typed 2030 is told (today itself is allowed: that's what `in_progress` is for); days before an employee's `join_date` are skipped for that employee, not errored, and days after their `left_on` keep no row (the builder removes any — see Employee lifecycle). Why: both used to accept any date, and a punch 30 days before hire, or a build for 2030 (35 `absent` rows for a date that hadn't happened), wrote real-looking `daily_attendances` rows into the one table treated as derived truth, with no way afterwards to tell invented rows from real ones.

**An imported punch outside the employment period is kept** (Phase 3a): a device or CSV punch dated before an employee's `join_date` or after their `left_on` is still written to `attendance_logs` — raw hardware facts are never dropped — but the builder keeps no row for that date, and `attendance:import` prints the count as an "Outside employment" warning line (`IngestionSummary::$outsideEmployment`). Only a manual punch is rejected outright (above).

**The CSV import path doesn't assume a well-formed file** (`CsvAttendanceSource`, driven by `attendance:import`). A row whose field count differs from the header (a truncated final line, a trailing comma), a missing `device_user_id`/`punched_at`, or a date that doesn't exist (`2026-02-30`, month 13, hour 25) is recorded in `errors()`, skipped with its line number, and printed in the import summary — every other row still imports. Impossible dates are caught by `App\Support\StrictDate`, because `Carbon::createFromFormat` silently rolls them over (`2026-02-30` becomes `2026-03-02`), which would write a plausible-looking wrong punch into the append-only log that nothing downstream could ever detect. It checks PHP's parse warnings rather than doing a strict round-trip, so real but unpadded input like `2026-1-5` is still accepted. `attendance:build-daily`'s `--date`/`--from`/`--to` use the same check. Two file-level cases abort with a clear `AttendanceImportException` instead: an error the reader didn't anticipate (e.g. a bad `punch_type_map` value) names the line it happened on, and an unopenable file says "Unable to open attendance CSV" — its `fopen()` is `@`-suppressed on purpose, since Laravel would otherwise turn the warning into an `ErrorException` before that check could run.

**`daily_attendances` builds itself** (Phase 2.5a). Before this, a row existed only if someone ran `attendance:build-daily` by hand, so the dashboard read "Not calculated", and a day built as `in_progress` never became `absent`/`incomplete` because nothing rebuilt it after `end_time`. Now, in `App\Console\AttendanceSchedule` (wired through `withSchedule()` in `bootstrap/app.php`), run by the `scheduler` service against the dev `stampy` database, in the app timezone:
- **Every 15 minutes: today** (`attendance:build-daily --date=<today>`). This is what moves an `in_progress` day to its final status once it closes, and picks up punches imported during the day.
- **Every 15 minutes, while yesterday has any `in_progress` row: yesterday** (Phase 2.7, `--date=<yesterday>`, gated by a `when()` checked on each tick). An in-only day closes at first in-punch + 18h, which can be after midnight (a 9:30 in-punch closes at 03:30); this closes it within 15 minutes instead of waiting for 02:10 — or, for that 9:30 punch, the next night.
- **Daily at 02:10: the last 7 days** (`--from=<today−6> --to=<today>`) — a window, not just yesterday. The command's default range is yesterday and today, so if the server were down for three days those days would never be built; the builder is idempotent, so re-running a week costs nothing and heals any gap inside the window with no state to track.
- All three use `withoutOverlapping()`, with the lock capped (10, 10 and 60 minutes) so a killed run can't block its task for the 24h default. A non-zero exit is logged with the command's output: `Log::error("Scheduled attendance rebuild (…) failed: …")`. The dates are computed when the schedule is registered, which is every minute (`schedule:work` starts a fresh `schedule:run` per tick), so "today" is never stale. Evidence it runs: `docker compose logs scheduler`; what's registered: `docker compose exec app php artisan schedule:list`.
- **Gaps older than 7 days are not healed automatically** — nothing else would ever come back for them, and more machinery isn't worth it. Backfill by hand: `docker compose exec app php artisan attendance:build-daily --from=YYYY-MM-DD --to=YYYY-MM-DD` (never in the future; for one employee add `--employee=<id or code>`).

**An import rebuilds what it touched, once, at the end** (`attendance:import`). The range is the earliest to the latest newly imported `punched_at` date, widened by one day each side (an imported punch can pair into the previous day through the 18h overnight window, and change the next day's "claimed by an earlier shift" result), for **every employee active on any date in it** (`Employee::scopeActiveBetween()`) — so someone with no punches in the window is marked absent rather than left "not calculated". The summary prints the range. `--dry-run` rebuilds nothing, and an import that adds nothing (all duplicates) rebuilds nothing. If the rebuild fails (`NoScheduleAssignmentException` — see the `employee_work_schedules` section above; not a missing default, which can only happen at employee-creation time now) the punches are kept (they're already written), the command exits 1 and says to run `attendance:build-daily` once that's fixed.

**The D-1/D/D+1 window has one home** — `DailySummaryBuilder::rebuildAround()`, used by both a manual punch (`Attendance\Show`) and an import — and it is clamped to the employee's real history: never before `join_date`, never after today. The clamp exists because the old manual-punch copy of this rule was not clamped: a punch added today on someone's hire date created a row for the day *before* they were hired (`off`) and a row for *tomorrow* (`absent`), the same invented-row defect as the date-range rules above. (This clamps a window the code derives, not a range the operator typed, so it doesn't conflict with `build-daily` refusing to silently clamp an operator's dates.)

Three model decisions here aren't obvious from the schema alone, and have already been re-litigated at least once — recorded so they aren't re-opened again:
- **`attendance_logs` is append-only.** A correction is a void (`voided_at`/`voided_by`) plus a new row, never an edit to an existing one — preserves a full audit trail of what the device actually reported vs. what an admin corrected, and is what makes `daily_attendances` safely recomputable at any time.
- **Status answers "did they attend"; timing is a separate dimension.** `AttendanceStatus` has no `Late` value — a day with `late_minutes`/`early_leave_minutes` > 0 keeps its own status (`present`, or, since Phase 2.6, `in_progress`/`incomplete` for late), and a holiday's timing fields are forced to 0 by the builder for every status, so it can never register as a timing exception either. **Timing does not need both punches:** late is a fact about the in-punch (the `first_in` the builder's pairing already chose) and is recorded as soon as it exists, and it never disappears when an `in_progress` day later becomes `incomplete`; early leave is a fact about the out-punch of a worked shift and is only recorded on `present` days. An out-only day has neither. See the "Status vs. timing" note under Design system for the full reasoning; `DailyAttendance::displayVariant()` is what every view colours from, so this distinction isn't just a data-modeling footnote — it's the one thing every Attendance view must route through.
- **Status precedence, highest to lowest** (`DailySummaryBuilder::calculate()`, where the full comment lives): **(1) `off`** — no punches at all and not a scheduled workday, holiday or not. **(2) `holiday`** — no punches at all, a workday, holiday-marked. **(3) `present`** — both punches exist, on any day; a holiday only zeroes its timing, it doesn't need to override the status. **(4) `leave`** (Phase 3d) — an approved full-day leave covers the date (an AM and a PM leave together count as one) and fewer than both punches exist: `leave` from 00:00, never `in_progress`, so never "due" or "Not in yet"; a single punch doesn't make it `incomplete` (the punch stays stored, and the day is flagged as worked on leave). Both punches on a leave day are `present` (3), with no timing — like a holiday, there was no expected window — and an off day or holiday inside a leave stays `off`/`holiday` (1–2). A `leave` row carries no timing and no worked minutes. **(5) `in_progress`** — the day is still open, and punches so far would otherwise resolve to (5) or (6). Since Phase 2.7 "open" depends on the punches: an in-only day stays open until its pairing window closes (first in-punch + `MAX_SHIFT_HOURS`, 18h — past the schedule end and past midnight, so someone on overtime is still at work and a (+1) out-punch turns the day `present` with no `incomplete` in between); a punchless or out-only day is open only today, until the schedule's `end_time`. **(6) `incomplete`** — exactly one of {in, out}, on any day, holiday or not — a missing punch is a device-defect fact independent of whether the day was a holiday. Precedence did not change in Phase 2.6; only which statuses can carry `late_minutes` did (see the bullet above). **(7) `absent`** — a workday, no punches, none of the above applied. Someone who works a non-workday (an ordinary weekend or a weekend holiday) is (3), not (1) — that already worked before holidays or in_progress existed and neither changes it.
- **Known, accepted limitation: a same-day in/out pair more than 18h apart shows as `incomplete`.** `MAX_SHIFT_HOURS` (18) bounds how far after an in-punch an out-punch may be and still pair with it. An in at 00:00:00 and an out at 23:59:00 on the same day are 23h59m apart, so the out is never paired: `last_out` is null, `worked_minutes` is 0, status is `incomplete` — and nothing on the row records that an out-punch existed and was excluded. This is the window working as designed, not a bug. The punch itself is intact in `attendance_logs` and listed in the day's raw punches on `Attendance\Show`, so if you're debugging an inexplicable `incomplete`, look there for an out-punch more than 18h after the in-punch. Deliberately no "excluded punch" indicator for now; revisit only if genuine ~24h shifts turn up.
- **Known, accepted limitation: no overnight schedules.** `WorkSchedule` rejects `end_time <= start_time` outright (`InvalidWorkScheduleException`) — `DailySummaryBuilder`'s late/early-leave arithmetic (`calculate()`) assumes a shift starts and ends within the same calendar day; a genuinely overnight schedule (say 22:00–06:00) would compute silently wrong numbers rather than fail loudly. Like the 18h limitation above, this is a deliberate boundary of what the builder supports today, not an oversight — revisit only if a real night-shift schedule is needed, and treat it as a builder change, not just a validation relaxation.

### Phase 3b (built) — counting, entitlements, balances, grants

No schema change; services in `App\Services\Leave` (the rules are Phase 3's Policy rules 3–7 and 10, below).

**Day amounts are integer tenths of a day, never floats** (`App\Support\LeaveDays`): 18 days is `180`, a half day `5`. Every stored amount is `decimal(_,1)`, so tenths hold each exactly, and the only rounding the rules have — "up to the next 0.5" — is integer arithmetic (`LeaveDays::ceilToHalf()`, `ceil(n ÷ (d × 5)) × 5`) with no representation error at the boundary, where a float would turn 15.5 into 15.499… and round it the wrong way. Convert only at the edges: `fromDecimal()` for a `decimal:1` cast or a `SUM()` string, `toDecimal()`/`format()` for storage and display.

**`App\Support\WorkdayCalendar`** is the one definition of a working day: `isScheduledWorkday()` (a workday of the schedule — the builder's `off` test), `isHoliday()` (the builder's `holiday` test), and `isWorkday()` = both, for the schedule in force on the date (`scheduleOn()`). `DailySummaryBuilder` asks the two halves separately (they have different precedence); leave counting asks them together. Extracted from the builder in 3b with its behaviour unchanged.

**`LeaveDayCounter`** — what a leave costs, **split by calendar year** (`[2026 => 20, 2027 => 10]` for Wed 30 Dec – Sun 3 Jan): a `workdays` type counts `WorkdayCalendar::isWorkday()` dates, so a schedule reassignment mid-leave is handled per date; a `calendar_days` type (Maternity) counts every date; a half day counts 5 if its date counts. Derived, never stored — a holiday added inside an approved leave refunds the day with no other step.

**`EntitlementCalculator`** — the grant for (employee, type, year), pure (no writes; depends on `join_date`, the type and the year only). Returns an `Entitlement`: `noBalance()` (no `days_per_year`), `notEligible(eligibleOn)` (a year before the eligibility year), or `grant(days, eligibleOn)`. A year's allowance is `days_per_year` plus the seniority bonus (+1 per 3 completed years as of 31 Dec, which is simply year − join year); a partial year is pro-rated by days employed ÷ the real year length (366 in a leap year) and rounded up to the half day, each year on its own. `eligibleOn` is `join_date->addMonthsNoOverflow(min_service_months)` (29 Feb → 28 Feb), or `join_date` with no requirement; the eligibility year's grant folds in the join year pro-rated, any full years between and the eligibility year in full (1 Mar 2026 → 33.5 in 2027). `earnedToLastDay()` is the same calculation cut at `left_on`, for display: for a leaver before eligibility it folds in every year since joining (days earned but never usable). Its partial last year pro-rates the whole allowance, seniority included.

**`LeaveBalance`** — a `Balance` for (employee, type, year): `entitled` (the grant row, or 0), `carriedIn`, `adjustments`, `used` (approved), `pending`, `available()` = entitled + carried in + adjustments − used − pending; `usedFromCarry`/`usedFromGrant` (FIFO — usage takes the carry first); `usedByType`/`pendingByType`; `usableFrom` (the eligibility date while it's in the future); `earnedToLastDay` (a leaver's last year). A type without `days_per_year` has no balance (`hasBalance` false); a deducting type's leaves (Special) count in its target's (Annual) `used`/`pending`. **Carry-over is derived:** into year Y, min(cap, what was left of Y−1), where left = entitled + carried in + adjustments − **approved** usage, never below 0; no cap → no carry; the eligibility year's remainder carries **uncapped** (its grant may arrive with weeks left), the cap applying from the next year; the chain stops at the first year with no grant row. So cancelling last year's approved leave raises this year's carry with no other step.

**`LeaveGranter`** — the one place a grant row is created automatically. For (employee, year, as-of date) it creates each missing grant for every **active** type with a balance whose `Entitlement::isGrantableOn(asOf)`; existing rows are skipped (idempotent). It skips an employee not active on the as-of date, and an early (later-year) grant for anyone with a `left_on`. Used by:
- **`leave:grant {--year=}`**, scheduled **daily at 00:05** by `App\Console\LeaveSchedule` (wired in `bootstrap/app.php` next to `AttendanceSchedule`, the same way: `withoutOverlapping(30)`, a fixed output file, a non-zero exit logged). Daily, not only on 1 Jan, because eligibility dates fall all year — and because it checks "eligible and no row", a missed run catches up the next day. `--year=<next year>` grants early. A past year is refused: grants are only ever created for the current year or later, so balances from before the system went live go in as admin adjustments.
- **`Employee::booted()`**: a new employee gets this year's grants in the same transaction as the insert (with no leave types configured it creates nothing and doesn't throw — unlike a missing default schedule). A changed `join_date` re-grants (`regrantAfterJoinDateChange()`): the automatic rows (`granted_by` null) for the current and later years are deleted and granted again from the new date, in the same transaction as the update — `Employee::save()` wraps an update that changes `join_date` for this; earlier years, admin-entered grants and adjustments are untouched; a leaver is re-granted as of their last day.

**`leave:balance {employee} {--year=}`** — read-only: every type's balance for one employee (by `employee_code`), for HR and for checking by hand.

`LeaveTypeSeeder` runs **before** `EmployeeSeeder`, so seeded employees get their grants through the creation listener; `DatabaseSeederTest` asserts each seeded employee holds exactly the grants the calculator says they're eligible for today (shown to fail with the seeders in the wrong order).

### Phase 3c (built) — approval engine and request lifecycle

No schema change. The engine (`App\Services\Approval`) is shared; request data isn't (Phase 3 rules 8–15).

**`App\Contracts\Approvable`** — what the engine needs from a request, and no more: `approvalSubject()` (the employee it's for — step 1 is their manager's), `approvalSteps()` (the `approval_steps` morph), `currentApprovalStep()`. `Leave` implements it; Phase 4's overtime request will too.

**`ApprovalFlow`** — who decides each step, and the one way a step is recorded (`record()`):
- **Step 1** (`MANAGER_STEP`): users with the **manager or admin role** whose employee `isManagerOf()` the requester — transitive, so a skip-level manager can act; never a second walk of the reporting chain. An employee-role user who is someone's `manager_id` is **not** an approver (they can't see that employee anywhere — `EmployeeScope`).
- **Step 1 is skipped** (a `skipped` row, `decided_by` null) when it has nobody, with the reason as the note: "No manager is assigned to …", "… manages … but doesn't have the manager role" (a setup mistake an admin should see), or "No one who manages … has a login".
- **Step 2** (`ADMIN_STEP`): admins. Nobody decides a step of their own request; a requester who is the **only** admin has step 2 recorded as `self_approved` — after step 1, which still runs (their manager approves first).
- **An admin's decision at step 1 covers both steps** (`decidesBothSteps()`): two rows, both theirs — an override, or a manager who is also an admin.
- **Eligibility is evaluated at decision time, never snapshotted at submit.** If the chain changes while a request waits (a role removed, a move to another team) and nobody is eligible any more, it stays at step 1 for an admin's override. `Employee` forgets its memoized `subordinateIds()` whenever a `manager_id` changes, so a move earlier in the same request is seen.

**`ApprovalInbox`** — `for(User)` returns three groups the Approvals page shows separately: `stepOne` (step-1 requests from the people they manage), and for admins `stepTwo` and `overrides` (other step-1 requests they could decide in the manager's place). Never the user's own; each group sorted by start date, soonest first, overrides with the stuck ones first. `count()` is what waits **on this user** — the sidebar badge, the menu-button dot and the dashboard's Pending approvals card (3e): step 1 for their team, and for an admin step 2 plus only the **stuck** overrides — waiting two of the requester's working days since submission, starting within two working days (or already started) — from its **stuck deadline**, the second of the requester's working days before it starts — or with **every eligible step-1 approver on approved full-day leave today and none of them back before that deadline** — the commonest stall (3f: an approver back in time to decide doesn't make it stuck) (`isStuck()`). Whenever the approvers are all away the item says who and until when, the end of their continuous absence ("Aye Aye Mon (manager) is on leave until Tue 6 Oct", `awayReason()`), stuck or not. Counting every override would put every pending request in the company on an admin's badge. A query each time.

**`LeaveRequestService`** — the lifecycle. **Every mutation locks the employee's row first (`lockForUpdate`), then the leave's**, so two concurrent submits for the same employee serialize their read-then-write balance and overlap checks; `approval_steps`' unique index backstops a double decision. Authorization goes through `LeavePolicy` inside the service too.
- **`submit()`** validates in stages, the first failing stage throwing (later checks never see input an earlier one rejected): the type is active and the actor may file (`create`); `end ≥ start`; the employment period (`join_date ≤ start`, `end ≤ left_on`); at most `RETROACTIVE_DAYS` (30) back for a non-admin; no later than 31 Dec, or next year's 31 Dec once next year is granted; the service requirement of the type or its target (the message names the date); half-day rules (the type allows it, a single date, and that date's schedule has a `break_start`); the cost (`LeaveDayCounter`) is non-zero and within `max_days_per_request` in the type's own counting; no overlap with pending/approved leave at half-day granularity (an AM and a PM on one date coexist); each year's cost within that year's `available()` of the type holding the balance. A normal request starts at step 1 (or records the skip and moves to step 2, self-approving a sole admin's); **an admin filing for someone else is approved on submit**, both steps theirs.
- **`approve()` / `reject()`** take an optional `$expectedStep` (the step the actor saw): a request no longer pending, at another step, or whose step was just recorded by someone else fails with **`StaleLeaveDecisionException`** — a readable message, never a unique-index crash. Rejecting at any step ends the request (nothing to rebuild).
- **`cancel()`**: the requester (the employee the leave is for) before its start date, an admin at any time; `cancelled_by`/`cancelled_at` set, the steps left as they were.
- **Write first, then rebuild** (the `EmployeeScheduleAssigner` pattern): when a leave becomes approved, or an approved one is cancelled, its days — `max(start, join_date)` to `min(end, today, left_on)`, nothing for a future leave — are rebuilt after commit through `DailySummaryBuilder::rebuildBetween()`. A failure is returned as `rebuildError`, logged ("Leave #… approval for …: rebuild failed partway …"), and names the `attendance:build-daily --from --to --employee` command; the decision stands. The rebuild is what turns the leave's days into `leave` rows (3d).
- **Deactivation settles leave** (`deactivationEffects()` / `applyDeactivation()`, called by `EmployeeLifecycle::deactivate()` in the same locked write as the status change): a pending or approved leave that **starts after `left_on`** is cancelled (`cancelled_by` the admin); one that **spans** it is cut to end on `left_on`, or cancelled if that leaves no working day. Reactivating doesn't restore them.

**`LeaveValidationException`** — the shape a form reads: `errors()` is `array<string, list<string>>`, keyed by field — `leave_type_id`, `start_date`/`end_date` (dates, eligibility, cost, overlap), `half`, and `leave` for the request as a whole (balance) — so a Livewire component adds each with `addError($field, $message)`, the way other components already surface a service's errors. `getMessage()` is the first message. `InvalidLeaveTransitionException` (from the model) and `StaleLeaveDecisionException` are separate: not input errors.

**`Leave`'s status transitions** are enforced on the model: `pending → approved | rejected | cancelled`, `approved → cancelled`, nothing else; `current_step` is set exactly while pending. Creation may take any status (an admin's filing is approved on submit).

**`LeavePolicy`**: `viewAny` (admins, managers, anyone with an employee record); `view` mirrors `EmployeePolicy::view`; `create` is self, or an admin for anyone (including employees with no login); `approve` is a pending request at a step `ApprovalFlow::canDecide()` allows; `cancel` per the rule above. Lists use `Leave::scopeVisibleTo($user)` — `EmployeeScope`'s rule.

**`Employees\StatusModal`** turns that into a **two-step confirm** when leave is affected: the first Deactivate lists the leaves that will be cancelled or shortened without writing; the second recomputes and writes — unless the list changed in between (`AffectedLeavesChangedException` inside the lock, or a mismatch before it), in which case the new list is shown and confirmed again; a new last day starts over. With nothing affected it stays one click. The date picker is unchanged (still deferred).

### Phase 3d (built) — leave in the attendance builder

One alter-migration (`daily_attendances.leave_id`, above). Approved leave is one more builder input; `daily_attendances` stays derived, and a rebuild of any range gives the same rows as building it fresh. Days no approved leave covers are untouched — proved with a `daily_attendances` hash, identical before and after (Phase 3d, built, below).

**`LeaveDay`** (`App\Services\Attendance`) — what approved leave means for one date: `fullDay` (a whole-day leave, or an AM and a PM leave together, which leave no expected window either), the one `half` on leave, and the `leaveId` for the row (the whole-day one, else AM, else PM). Pending, rejected and cancelled leave never reach the builder. A range build loads the employee's approved leave **once** (`DailySummaryBuilder::approvedLeavesBetween()`, used by `buildRange()` and `attendance:build-daily`) and passes it to `build()` for every date; a lone `build()` loads its own.

**`ExpectedWindow`** — the one definition of when someone is expected at work, read by the builder and by `DailyAttendance`: `start_time`–`end_time`, or on a half-day leave the half worked (Phase 3 rule 19): **AM leave** from the PM start (`break_start + break_minutes`), **PM leave** until `break_start`. On a half-day leave day:
- **late** counts from the window's start + grace (AM leave: 13:10 with 10 minutes' grace is on time, 13:11 is 11 minutes late — truncation unchanged);
- **early leave** counts against its end (PM leave: leaving at 12:00 isn't early, nor is 12:30);
- **a punchless day** is `in_progress` until the window's end — the schedule end on AM leave, **12:00 on PM leave, then `absent`** (the morning was missed);
- **worked minutes** subtract only the span's **overlap with the break window** (arriving at 13:00, or leaving at 12:00, subtracts nothing). **Full days keep the flat rule** — the whole `break_minutes` off however the day was punched — unchanged;
- an in-only day follows Phase 2.7's pairing window as usual; status is `present`/`incomplete`/`absent`/`in_progress`, never `leave`, with `leave_id` set and the half as an annotation, never the colour (rule 18).

**A half-day leave never sits on a schedule without `break_start`.** Submitting one is refused (3c), and so is any schedule change that would put a pending or approved half day on such a schedule: `EmployeeScheduleAssigner::assign()`, `bulkReassign()` and `Employees\ScheduleAssignments::deleteAssignment()` throw `HalfDayLeaveNeedsBreakException` before writing anything, naming the leaves and the schedule and saying to set "Break starts" there first (allowed once even on a locked schedule, 3a). Why: under the builder's fallback a punchless PM-leave morning would build as `absent` and land in Needs attention — unfair to the employee — and nobody reads a log warning. The fallback still exists, defensively: a half day on a break-less schedule is built by the ordinary rules, keeps `leave_id`, and logs a warning naming the leave.

**`DailyAttendance`** gains derived facts, none of them a status:
- `leaveDay()` (every approved leave covering the date, so an AM+PM date reads as full; `withLeaveDays()` resolves a list in one query) and `expectedWindow()`.
- **`workedOnLeave()`** — "worked on approved leave": any punch on a full-day leave (AM + PM included), an in-punch before `break_start` on AM leave, an out-punch after the PM start on PM leave. Arriving at 11:55 on an AM-leave day counts; it's an annotation, the admin decides whether to cancel the leave, and the balance is never refunded automatically. No acknowledge state: kept, it just becomes history.
- **`isNotInYet()` / `notInYetAfter()`** use the window's start: an AM-leave person is due at 1:00 PM (+ grace), and Needs attention says `due 1:00 PM`.
- `isAwayOnLeaveNow()` — a punchless In progress row on AM leave before the PM start + grace.

**`DashboardAttendance`**: Needs attention lists today's worked-on-leave rows last, plain text (`Punched on approved leave`), counted in the header total; past days never appear there — the attendance views annotate them, and Daily attendance's **Worked on leave** filter finds them (3e). The live strip's `{n} on leave` counts full-day `leave` rows plus punchless people still inside their AM leave — after the PM start + grace they're `due` — so Not in's sub-line stays a partition. The rate's denominator: Phase 2.7 item 6.

**The month summary** (`AttendanceSummary`, since 3e — My attendance and the employee dashboard share it): Calculated workdays = present + absent + incomplete + **leave** (rule 20), so the four status counts add up to it ("On leave" is the `leave` count). How much leave was taken is a separate figure (`leave_tenths`), shown on its own line as "Leave taken: N days" — full days 1, half days 0.5; a half-day Present day is one workday and 0.5 leave; an off day or holiday inside a leave is neither.

¹ **Row-level scoping — the rule Phase 3 approvals will be built on.** A manager sees only **themself plus their transitive subordinates**: everyone reachable down `employees.manager_id` (`Employee::subordinateIds()`, walked level by level with a visited set and a depth cap of 10, so a cycle can't loop). It is enforced in two places that must agree: `EmployeePolicy::view` (used by `Employees\Show` and `Attendance\Show`: admin → yes; own record → yes for any role; manager → `isManagerOf()`; otherwise no) and, for lists and figures, `App\Support\EmployeeScope::for($user, $context)` (admin → no restriction; manager → themself + reports; any other role → their own record; a user with no linked employee record → an empty scope and a logged warning). `EmployeeScope` is the one definition of the list rule and is used by `Attendance\Index`, `Employees\Index` and the dashboard's attendance and headcount figures in `routes/web.php`; `EmployeeAccessScopingTest` checks it against `EmployeePolicy::view` for every kind of user, so the two can't drift apart silently. A manager with no linked employee record is denied by the policy and gets an explicit "Your account isn't linked to an employee record" state (`x-no-employee-record`) on the attendance list and the employee directory, not a bare empty table. Anything that asks "is this person one of my reports?" — leave approval included — must reuse `isManagerOf()`/`subordinateIds()`, not define "reports" a second time.

² The Employees directory **is** row-scoped through `EmployeeScope`: rows, the Total/Active/Inactive figures, and the department filter's options all cover only the viewer's team, so every row a manager sees links to a page they may open. The **dashboard's** Total employees / new-this-month cards use the same scope, so a manager's dashboard headcount agrees with the directory's team total instead of describing the whole company.

³ `Employees\ScheduleAssignments` (the profile's Schedule card) reuses `EmployeePolicy::view` for the whole component — whoever can open the profile at all can see the assignment history, same as Department/Position/Manager/Login — checked in `mount()` and again in `render()` (see the Authorization convention: nesting inside `Employees\Show` doesn't exempt it, since its own update requests never route through the parent). Only the mutating actions (`create`/`assign`/`deleteAssignment`) additionally check `EmployeePolicy::update` (admin-only), the same ability that already gates manual punches, password resets and editing the employee record itself — a manager sees the history but no assign/delete controls. `EmployeeScheduleAssignmentsComponentTest::test_a_page_opened_while_authorized_stops_serving_data_once_access_is_revoked` constructs the mid-session-revocation scenario against this component directly, the same way `EmployeeShowTest`'s identically-named test does for the parent.

**A link, card or row shown to someone who cannot open its target is a bug, whether or not it ever gets clicked — and the fix is always to gate by the ability the destination itself enforces, never a role list at the call site.** A role list at the call site and the destination's real gate are two independent facts that only happen to agree today; the first time someone changes one without the other, they drift, and the UI keeps offering a route that 403s. Found and fixed this way three times so far, each a slightly different shape of the same mistake: the Employees directory originally listed every employee to every manager rather than scoping rows to their own team, fixed by routing every list through `EmployeeScope` (¹ ² above) instead of a per-page role check; `Attendance\Show`'s "Back to attendance" link rendered unconditionally, including via `/my-attendance`, which no `role:` middleware or policy would have caught since the component itself is reachable by everyone — fixed by gating on the route actually reached (`request()->routeIs('attendance.mine')`), not a role; the dashboard's "Quick Actions" card rendered all four of its links whenever `$stats` was set, which is true for `admin` **or** `manager`, while two of those links (`organization.index`) are `role:admin` only — fixed by filtering each action through `$user->can(...)` against the exact ability (`EmployeePolicy::create`/`viewAny`, `DepartmentPolicy::viewAny`) its destination page itself checks in `mount()`, and hiding the whole card rather than leaving a manager with one action that only duplicates a sidebar link they already have. When adding a new link, card or row: ask what ability its destination checks, and gate on that ability directly — not on whichever role happens to reach the page today.

Editing employees, punches, holidays and the like is admin-only through `update`/`create`/`deactivate`/`delete` on the policies; `EmployeePolicy::update` is also what gates manual punches and password resets. Separately, every signed-in route except password change and logout is blocked while a user's `must_change_password` is set (the global `EnsureMustChangePassword` middleware).

Enforced in four places, none of which is optional:
1. **Route middleware** — `role:admin|manager` / `role:admin` groups in `routes/web.php`. `/my-attendance`, `/profile` and the password routes need only a signed-in user (`auth`); there is no `verified` middleware anywhere (see Tech stack).
2. **Policies, via `$this->authorize(...)` in Livewire components** — in `mount()`, again in every mutating action, and in `render()` for `Attendance\Show`, `Employees\Show` and `Employees\ScheduleAssignments` (see the Authorization convention, and ³ above for why the last of those skips the `mount()` check the other two have).
3. **Row-level query scoping** — `EmployeeScope`, used by the attendance list, the employee directory and the dashboard's attendance figures, per ¹.
4. **The UI** — the sidebar (`hasRole(...)`) and `@can` in Blade hide controls a user can't use. This is presentation only; it is never the gate, and a hidden button must always be backed by an `authorize()` in the action.

**Phase 2.6, built: live today — late on the in-punch, "Not in yet".** Problem: late minutes were only computed once a day had both punches, so a late arrival was invisible while the day was in progress (the dashboard's Needs attention stayed empty mid-day), and employees who hadn't arrived yet were hidden inside `in_progress`. Owner decisions:
1. `late_minutes` is computed whenever the day has an in-punch — `in_progress`, `incomplete` and `present` — and stays on the row when an `in_progress` day later becomes `incomplete`: a late fact never disappears.
2. `early_leave_minutes` stays present-only (it isn't knowable before the out-punch).
3. A day with only an out-punch has no late (no in-punch) and no early leave.
4. The holiday rule extends: on a holiday-marked day timing is forced to 0 for `in_progress` and `incomplete` as well as `present`.
5. Status is unchanged: no new `AttendanceStatus` value, precedence unchanged, `displayVariant()` unchanged (colour = status only). Late stays an annotation.
6. **"Not in yet" is a derived display fact, never a status and never "absent":** an `in_progress` row with no punches whose schedule `start_time + grace_minutes` has passed (app timezone). Before that point the person is simply in progress. *(Since Phase 3d the start is the expected one — the PM start on an AM-leave day — and a full-day leave is `leave`, never "not in yet".)*
7. Grace and truncation are unchanged (late begins strictly after grace; `intdiv`, never round).
8. The builder's existing in/out pairing decides which punch is the in-punch; no second pairing rule.

Scope: `DailySummaryBuilder::calculate()` (1–4, 7–8) with its comment and this file's schema/precedence wording updated; `isLate()`/`hasTimingException()` follow the new `late_minutes`, `leftEarly()` unchanged; a backfill of historical incomplete days with the existing `attendance:build-daily` (no migration); UI — the Attendance table's Late column and the "Late arrival" filter include `in_progress`/`incomplete` rows, the calendar/modal mark the in-time on those days, the dashboard's Needs attention lists late arrivals today then "Not in yet · due 8:00 AM" (Phase 2.7 later put Absent and Incomplete first — see `docs/ATTENDANCE_UI.md`, Needs attention), and the live strip shows a late sub-line on At work and Left (an annotation on a partition group, never a fourth group) with the dashboard's Employees cell removed and three cells in one row at every width. "Not in yet" has two documented scopes: the strip counts every active employee with no punch yet today; Needs attention lists only those past `start_time + grace_minutes` — always a subset of the strip's count, never a different definition under the same label.

**Phase 2.7 — Day close (built).** Problem: after a schedule's end time the builder closed every row at once — an in-punch-only row became `incomplete` at 17:00 even when the person was still at work on overtime, although the builder would still pair an out-punch up to 18h after the in-punch (the "(+1)" overnight out); and the dashboard, once today's rows were final, contradicted itself (a live "Not in yet 35" strip beside 8 Absent rows, 0% bars with no marker). Owner decisions:
1. **An in-only row stays `in_progress` until its pairing window closes** — first in-punch + `MAX_SHIFT_HOURS` (18h), even past the schedule's end and past midnight — and only then becomes `incomplete`. This keeps overtime workers "at work" and matches the existing out-punch pairing exactly, so an out at 00:42 (+1) turns the row `present` with no `incomplete` in between.
2. A row with **no punches** still becomes `absent` at the schedule's end (unchanged); an out-only row keeps its rule (today, before end).
3. Late on `in_progress` rows stays as Phase 2.6 made it; early leave still needs both punches.
4. **Scheduler:** the 15-minute job also rebuilds **yesterday** while yesterday has any `in_progress` row, so a late in-punch (9:30 → window closes 03:30) is closed without waiting for the 02:10 run.
5. **The dashboard follows the builder's statuses** — one source of truth, consistent with the attendance table: an Absent row shows as Absent. The live strip's third cell becomes **"Not in"** (active employees with no punches today — the strip is a partition by punches, so an out-only day is Left) with a sub-line by state — `{n} due` (punchless `in_progress`, plus anyone not built yet), `{n} absent`, both when mixed (since Phase 3d also `{n} on leave`, which includes a punchless person on AM leave until the PM start + grace); **"At work"** adds `{n} past end time` for `in_progress` rows whose schedule end has passed (since Phase 3e the expected end, `ExpectedWindow` — noon on PM leave). The partition and its sum rule are unchanged. Needs attention shows "Not in yet · due 8:00 AM" only for punchless `in_progress` rows past start + grace, an Absent badge for Absent rows, and its header shows the real total (the list stays capped at 8, most urgent first).
6. **Attendance rate = attended ÷ active employees, attended = present + incomplete**, for the trend bars and the Department card. *(Refined in Phase 3d, settled with the owner in 3e:)* **a person on full-day approved leave is left out of the denominator M unless they're counted in N**, in the trend and in the Department card's `N / M` — otherwise five people on approved leave would read as a 17% attendance drop on a 30-person day, a false alarm, and someone who came in on their leave day would put N over M (the seed once showed "Checked in 19 / 18"). Half-day leave stays in. While N is "checked in", anyone on leave with a punch stays in M; once N is "attended", a full day worked on leave is `present` and stays, a one-punch leave day stays `leave` and is out of both (`DashboardAttendance::expected()`). A day when everyone expected is on full-day leave shows a muted "Leave" marker on the trend, and a department whose whole headcount is on leave says "On leave" instead of `0 / 0`. A day with any `in_progress` row is pending: a lighter bar of attended so far (anyone with a punch, in or out) and a marker — "Today" for today, "Pending" for an earlier day still inside a pairing window. The Department card says "Checked in N / M" (any punch today, so the departments' total equals the strip's At work + Left) while pending and "Attended N / M" once closed — no bare percentage. A closed workday with 0 attended shows a small "0%" marker. A past day with no rows, or with `in_progress` rows whose window has already closed (the builder didn't run), shows a muted "Not calculated" marker — never 0%, never Absent. **"Active" means active on that day** (Phase 3a, `Employee::scopeActiveOn()`), in the numerator as in the denominator: each trend day, and `todayIsPending()`, counts the employees employed on it and only their rows, so a deactivated employee counts for every day up to their `left_on` and not after. (Until Phase 3a it meant active *now*, because there was no deactivation date: a deactivated employee's past days dropped out of the trend entirely. Mixing the two — rows of former employees in the numerator, current headcount in the denominator — had once lifted a past bar past 100%.)

Scope: `DailySummaryBuilder::calculate()`/`isInProgress()` and its precedence comment; `App\Console\AttendanceSchedule`; `DashboardAttendance` (strip, needs attention, trend, departments) and the dashboard view; the `in_progress` definition everywhere it's documented (this file's `displayVariant()` table and precedence, `docs/ATTENDANCE_UI.md`, `AttendanceStatus`); tests for each rule above.

## Phase 3 — Leave management (built)

Scoped 4 Oct 2026 from the "Open questions for Phase 3" section, which this one replaced. Owner decisions are marked **(owner)**; the rest are recommendations the owner accepted. Items still waiting on HR are listed at the end — they change seed data, not the design.

### Policy

1. **Leave year is the calendar year (Jan–Dec)** **(owner)**. Each year's balance is granted **upfront, once** **(owner)** — no monthly accrual.
2. **Leave types** (seeded; admin-editable under Policies). Annual, Unpaid and Medical are company policy **(owner)**; Special and Maternity follow the Cambodian Labour Law (Art. 166, 169/171, 182–183). HR still has to confirm the final list.

   | Type | Allowance | Counts | Carry-over | Half-day | Paid | Notes |
   |---|---|---|---|---|---|---|
   | Annual | 18 / year, +1 day per 3 completed years of service | workdays | yes, cap 6 | yes | yes | usable only after 12 months of service (rule 5) |
   | Medical | 30 / year | workdays | no | yes | yes | company policy; no certificate upload in Phase 3 |
   | Special | max 7 per request, **deducted from Annual** | workdays | — | yes | yes | family events (marriage, birth, illness/death of spouse, child or parent); needs Annual eligibility — before it, use Unpaid |
   | Maternity | 90 per request | **calendar days** (weekends and holidays included) | — | no | yes (50% — payroll's concern, not this app's) | no balance; no gender field exists, so eligibility is the approver's call |
   | Unpaid | no limit | workdays | — | yes | no | no balance |

3. **Carry-over is capped per type** **(owner)** (`carry_over_cap`, null = no carry). There is no "use carried days by date X" rule at this company **(owner)**. **Carried days are consumed first (FIFO).** With FIFO and a cap no larger than the yearly grant, a carried day is always used or dropped within one year, which already satisfies the law's limit on postponing leave (only days above 12/year, at most 3 consecutive years) — so no expiry field is needed. If a future type needs an explicit expiry, add it as a leave-type option then.
4. **Seniority bonus** (Annual only): +1 day per 3 completed years of continuous service, counted as of **31 Dec** of the grant year — the employee-favouring reading, same principle as minute truncation.
5. **Service requirement and mid-year joiners.** A leave type can require a minimum length of service (`min_service_months`). Annual requires **12 months**, per the Labour Law **(owner)**. The leave earned during that first year isn't lost; it becomes usable all at once on the **eligibility date** (`join_date` + 12 months; a 29 Feb joiner becomes eligible on 28 Feb, the employee-favouring reading).
   - **Nothing is granted before eligibility**, and an Annual request (or a Special one, which deducts from Annual) dated before the eligibility date is rejected.
   - **On the eligibility date**, a single entitlement row is created for that year. It holds the join year pro-rated plus every full year up to and including the eligibility year. Example: joined 1 Mar 2026 → eligible 1 Mar 2027 → the 2027 row is 18 × 306/365 = 15.09 → 15.5, plus 18 = **33.5 days**.
   - **Pro-rating:** `days_per_year × (days from join_date to 31 Dec, inclusive) ÷ days in that year`, **rounded up to the next 0.5**.
   - **First eligible year carry-over:** because a late-year joiner would otherwise get a large grant with only weeks left to use it, the **whole** unused balance of the first eligible year carries into the next year (the cap applies from then on). This is the default pending HR confirmation. FIFO still keeps every carried day under the law's 3-year limit.
   - **Types without a service requirement** (Medical, Unpaid, Maternity — subject to HR) are pro-rated in the join year and usable from `join_date`.
6. **Half-day leave is morning or afternoon** **(owner)**: AM 8:00–12:00, PM 13:00–17:00 on the default schedule **(owner)**. A half-day request is always a **single-day** request (`start_date = end_date`); a span that starts or ends on a half day is two requests. Counts as 0.5.
7. **Days are counted per employee per date**: a workday is a date that is a workday of `scheduleOn(date)` and not a holiday. Off days and holidays inside a leave never cost balance (except Maternity, which counts calendar days by law). The count is **derived, never stored**, so adding a holiday inside an approved leave refunds the day with no extra step.

### Approval

8. **Two steps: manager → admin** **(owner)**. "HR" is the existing `admin` role — no new role **(owner)**.
   - **Step 1:** the requester's manager. Anyone with the **manager (or admin) role** whose employee `isManagerOf()` the requester (the transitive chain, so a skip-level manager can act when the direct one is away) — never a second definition of "reports". *(Refined in 3c: the role is required, matching who `EmployeeScope` lets see that employee; an employee-role user who is someone's `manager_id` doesn't approve.)* Eligibility is evaluated at decision time, never snapshotted at submit: if nobody is eligible any more, the request waits at step 1 for an admin's override.
   - **Step 2:** any admin.
   - A requester with **no manager** skips step 1 (recorded as `skipped`). *(Refined in 3c:)* so does one whose chain has **nobody who can approve** — no login at all, or only employee-role logins; the skip's note says which, naming an employee-role manager, since that's usually a setup mistake.
   - A step-1 **rejection ends the request**.
   - An admin may **act at step 1** (manager unavailable): one decision completes both steps, recorded as such.
   - An approver who is **both the manager and an admin** completes both steps with one decision.
   - **Nobody approves their own request.** The one exception: if the requester is the **only** admin, their step 2 is recorded as `self_approved`, so a one-admin company can still take leave. *(Refined in 3c:)* `self_approved` replaces only step 2 — there's no second admin — and is no reason to skip the admin's own manager: step 1 runs as usual (or is skipped if they have no manager), a rejection there ends the request, and step 2 is recorded automatically when step 1 completes.
9. **An admin can file leave on behalf of any employee**, including employees with no login (Phase 1 requirement). It is recorded as entered by that admin and is final on submit.
10. **Pending requests reserve balance**: available = entitlement + carried in + adjustments − approved − pending. A request beyond available is rejected at submit (Unpaid and Maternity have no balance).
11. **No overlapping requests**: pending or approved requests for the same employee can't overlap at half-day granularity (an AM and a PM request on the same date are allowed).
12. **Cancel:** the requester may cancel a pending or approved request **before its start date**; after that only an admin can. Cancelling refunds the balance (derived — nothing to undo) and rebuilds the affected days.
13. **Retroactive requests:** allowed up to **30 days back** **(owner)** for employees and managers; admins may go back to `join_date`. Never before `join_date` or after `left_on`. Forward: only into years that already have entitlements (the grant command can grant next year early with `--year`).
14. **Notifications are in-app only** in Phase 3: a pending-count badge for approvers — *(refined in 3e)* on its own Approvals item, with a dot on the topbar's menu button below `lg` and a Pending approvals card on the dashboard, counting only what waits on that user — and, for employees, the "New" marker on Time off and the decisions card on the dashboard. No email (many employees have none) and no Telegram.

### Attendance integration

15. **`leave` comes only from `DailySummaryBuilder`.** Approved leaves become an input to the builder; nothing writes `leave` into `daily_attendances` directly, so the table stays fully recomputable. Final approval and cancellation **write first, then rebuild** the leave's dates (via `buildRange()` — built as `DailySummaryBuilder::rebuildBetween()` — clamped to `join_date`/today/`left_on`), with the same `rebuildError` reporting and logging as `EmployeeScheduleAssigner`. Pending requests never touch attendance.
16. **Precedence for a full-day approved leave:** `off` → `holiday` → `present` → **`leave`** → `in_progress` → `incomplete` → `absent`. So an off day or holiday inside a leave still shows as off/holiday (and costs nothing), and a full-day leave with no punches is `leave` from the start of the day — never "Not in yet", never absent.
17. **Punches on a full-day leave day:** both punches → `present` (the existing "both punches → present on any day" rule). Any punch on an approved full-day leave day is "worked on approved leave" (`DailyAttendance::workedOnLeave()`): today's are listed last in the dashboard's Needs attention ("Punched on approved leave"), and every day's is annotated in the attendance views and found with Daily attendance's **Worked on leave** filter. The balance is **not** refunded automatically — an admin decides whether to cancel the leave.
18. **A half-day leave day keeps its attendance status** (`present`/`incomplete`/`absent`/`in_progress`), with "AM leave"/"PM leave" as an **annotation**, never the cell colour — exactly as the Design system's status-vs-timing principle already anticipates ("partial leave later"). The expected window shrinks to the half worked:
    - AM leave: the day starts at the afternoon start — late is measured from 13:00 (+ grace).
    - PM leave: the day ends at the morning end — early leave is measured against 12:00; a punchless day is `in_progress` until 12:00.
    - Break minutes are subtracted only when the worked span covers the break.
19. **Half-day boundaries come from the schedule.** New column `work_schedules.break_start` (time, nullable): AM = `start_time`–`break_start`, PM = `break_start + break_minutes`–`end_time`. A half-day request on a schedule without `break_start` is rejected with a clear message. It is locked once referenced, like the other calculation fields. The migration backfills existing schedules (12:00 for the seeded 8:00–17:00); this is safe for locked schedules because the field is only read on half-day leave days, of which none exist yet — verify with a before/after hash of `daily_attendances`, as Phase 2.5c did.
20. **"Calculated workdays" includes leave**: `present + absent + incomplete + leave`, so "3 of 22 workdays taken as leave" is true. A summary's leave figure counts half days as 0.5.

### Employee end date

21. **`employees.left_on`** (date, nullable) — an alter-migration. Deactivating requires it (defaults to today); reactivating clears it. "Active on date D" becomes `join_date ≤ D` and (`left_on` is null or `D ≤ left_on`). The dashboard's 7-day trend switches to this rule, closing the Phase 2.7 open question. For a leaver, the balance view shows entitlement pro-rated to `left_on` against days used (including earned-but-not-yet-usable days for someone leaving inside their first year — the law owes them payment for those), so HR can see untaken or overused leave; the app takes no action on it. Existing inactive rows are seed data — backfill with their `updated_at` date. *(Added in 3c:)* deactivating also settles the employee's pending and approved leave after `left_on`, in the same write — a leave that starts after it is cancelled, one that spans it is cut to end on it (or cancelled if no working day is left); the deactivate modal lists them first (a two-step confirm). Reactivating doesn't restore them.

### Schema (all new tables are create-migrations; changes to existing tables are alter-migrations)

**`leave_types`** — `name` (unique), `days_per_year` decimal(4,1) nullable (null = no balance), `min_service_months` smallint nullable (null = usable from `join_date`), `seniority_bonus` bool, `carry_over_cap` decimal(4,1) nullable, `counts` enum(`workdays`, `calendar_days`), `max_days_per_request` decimal(4,1) nullable, `deducts_from_leave_type_id` FK → leave_types nullable, `allows_half_day` bool, `is_paid` bool, `is_active` bool, timestamps. A type anything points at — a leave, an entitlement, an adjustment, a type deducting from it — can't be deleted (deactivate instead); `counts`, `deducts_from_leave_type_id` and `allows_half_day` lock once a **leave** uses the type (two different tests, on purpose — see the Database schema section, Phase 3a). Changing `days_per_year` affects future grants only.

**`leave_entitlements`** — `employee_id`, `leave_type_id`, `year` smallint, `days` decimal(4,1), `granted_by` FK → users nullable (null = automatic), timestamps. Unique on `(employee_id, leave_type_id, year)`. The grant is a stored fact; usage and carry-over are derived.

**`leave_adjustments`** — append-only admin corrections: `employee_id`, `leave_type_id`, `year`, `days` decimal(5,1) signed, `note` (required), `created_by`, timestamps. Never edited or deleted — a wrong adjustment is fixed with a reversing one. Enforced in the model; `attendance_logs`, by contrast, is append-only by convention (see the Database schema section, Phase 3a).

**`leaves`** — replaced the old planning skeleton: `employee_id`, `leave_type_id`, `start_date`, `end_date`, `half` enum(`am`, `pm`) nullable, `reason` text nullable, `status` (`pending`/`approved`/`rejected`/`cancelled`), `current_step` tinyint nullable, `requested_by` FK → users, `cancelled_by` FK → users nullable, `cancelled_at` nullable, timestamps. Indexed on `(employee_id, start_date, end_date)` and `(status, current_step)`.

**`approval_steps`** — the shared half of the approval engine; Phase 4's `overtime_requests` reuses it. `approvable_type`/`approvable_id`, `step` tinyint, `outcome` (`approved`/`rejected`/`skipped`/`self_approved`), `decided_by` FK → users nullable (null for an automatic skip), `note` nullable, `decided_at`, timestamps. Unique on `(approvable_type, approvable_id, step)`. The request data stays in typed tables; only steps are shared. One service owns the state machine and approver resolution; `leaves` doesn't implement its own.

### Grants

- **`leave:grant {--year=}`** is idempotent (it skips existing rows) and runs **daily** at 00:05 (app timezone), not only on 1 Jan, because eligibility dates fall throughout the year. On 1 Jan it creates the regular grants; on any other day it creates first-eligibility grants (rule 5). An admin can also run it early for next year; employees not yet eligible are skipped.
- **A new employee gets this year's grants at creation**, in the same transaction — the `Employee::booted()` pattern the schedule assignment already uses. Refined in 3b: every type they're eligible for **as of creation**, not only types without a service requirement — so an existing employee entered with a past `join_date` gets a full year plus seniority, while someone joining today gets pro-rated Medical and Annual only once eligible. With no leave types configured it creates nothing and doesn't throw; the daily run catches up.
- **A corrected `join_date` re-grants** (added in 3b): the automatic grants (`granted_by` null) for the current and later years are deleted and granted again in the same transaction; admin adjustments and earlier years are untouched. This doesn't break "grants are stored facts": they're stored so a later change to a type's `days_per_year` can't rewrite past grants, and a corrected `join_date` is a corrected input.
- **The balance view shows the eligibility date** before an employee reaches it: "Annual: X days earned, usable from 1 Mar 2027".

## Phase 4 — Overtime (scope, not yet built)

Scoped 7 Oct 2026. Owner decisions are marked **(owner)**; the rest are recommendations the owner accepted. Rates and limits follow the Cambodian Labour Law and Prakas 112/25 (6 May 2025) until HR confirms the company's policy **(owner)**. Like leave types, every number below is a setting in Policies, never a constant in code.

### Policy

1. **Two ways to request** **(owner)**:
   - **Planned:** submitted before the overtime starts. This is the normal path; Prakas 112/25 expects overtime to be planned (employers notify the Ministry three working days ahead).
   - **Claim:** submitted after the fact, for unplanned overtime, up to **7 days** back (setting). Admins may go back further, as with leave.
   A request whose start time has passed when it's submitted is a claim. Both go through the same approval.
2. **Approval authorizes; punches decide the hours.** A request approves a window (date, start, end). The hours actually credited are the time the employee was punched in **inside that approved window and outside their expected working window**, never more than approved. Approve 18:00–20:00, leave at 19:20 → 1h 20m. Leave at 21:00 → 2h. No punches → nothing.
3. **Rates** (settings; Labour Law §139, §164):

   | When | Rate |
   |---|---|
   | Workday, outside night hours | 150% |
   | Night hours, 22:00–05:00 | 200% |
   | Weekly rest day (a non-workday of the schedule) | 200% |
   | Public holiday | 200% |

   - A window crossing 22:00 or 05:00 is split by the minute: 21:00–23:00 on a workday is 1h at 150% and 1h at 200%.
   - Rates don't stack: a holiday on a weekend at night is 200%, once.
   - The system records minutes per rate. It never computes money: there's no wage data, and payroll is outside this app.
4. **Pay or time off, chosen by the employee on the request** **(owner)**. The approver can change it when deciding (the step history records the change).
5. **Time off in lieu (TOIL)** **(owner)**:
   - **1:1.** One hour of overtime earns one hour off, whatever the rate (ratio is a setting).
   - Credited minutes accumulate per employee. **Every full 4 hours becomes 0.5 day** in a "Time off in lieu" leave type; the remainder keeps accumulating.
   - TOIL is taken exactly like Annual — same request flow, balance, half days.
   - The law expects a day off within the following week for rest-day work taken as time off (§151–152); the system shows the balance but doesn't enforce timing. HR to confirm.
6. **Limits** (settings; §137 and Prakas 112/25): at most **2 hours of overtime a day**, and at most **10 hours of work a day** including overtime. A request that would exceed either is refused for employees and managers; **an admin may override with a required reason** **(owner)**, recorded on the request.
7. **Voluntary.** Overtime is requested by the employee (or filed by an admin on their behalf with their agreement, as leave is). There's no "assign overtime" flow.

### Attendance integration

8. **The builder computes overtime**, so it stays derived and recomputable. New columns on `daily_attendances`: `overtime_request_id`, `overtime_minutes_standard` (150%), `overtime_minutes_premium` (200%). Approving, cancelling, or correcting a punch rebuilds the day.
9. **Outside the expected window** means outside `ExpectedWindow` for a workday. On a weekly rest day or holiday there is no expected window, so all approved, punched time counts (at 200%).
10. **Early arrival** counts only if an approved window covers it. Arriving at 07:00 for an 08:00 schedule isn't overtime by itself.
11. **Overnight:** overtime past midnight belongs to the work date of its in-punch, within the existing 18h pairing window. A window may end after midnight (e.g. 20:00–01:00).
12. **Leave days:**
    - No overtime request on a date covered by an approved full-day leave (the employee should cancel the leave first; "worked on leave" already flags the punch).
    - Half-day leave: overtime is only time outside the **full** schedule window, not the shrunk one. AM leave + work 13:00–19:00 → 17:00–19:00 can be overtime. HR to confirm.
13. **Incomplete days:** with no out-punch, no overtime is credited (the end time isn't known). It becomes credited once the punch is corrected.

### TOIL settlement

14. **TOIL credit follows the computed minutes, not the request.** When a day's overtime minutes change (approval, cancellation, punch correction), the employee's TOIL total is recalculated and the difference is posted as an **append-only, system-authored `leave_adjustments` row** linked to the overtime request. Never an edit.
15. **Cancelling approved TOIL overtime** whose days are already taken may push the TOIL balance negative. That's allowed and shown, like an over-used Annual; HR decides.
16. **The TOIL leave type** is seeded: no yearly grant, a balance built only from adjustments, half days allowed, workdays. Carry-over cap and expiry are HR settings.

### Approval and authorization

17. **Same engine as leave:** `approval_steps`, `ApprovalFlow`, manager → admin, every rule from Phase 3 rule 8 (no self-approval, sole-admin, override, approver-away stuck rule). `OvertimeRequest` implements `Approvable`.
18. **One Approvals page** for leave and overtime, with the type shown on each item. The badge counts both.
19. **`OvertimePolicy`** mirrors `LeavePolicy` (view, create for self or admin on behalf, approve, cancel). Cancel: the requester before the window starts, an admin any time.

### Schema

**`overtime_requests`** — `employee_id`, `date`, `starts_at`/`ends_at` (datetime), `kind` (`planned`/`claim`), `compensation` (`pay`/`time_off`), `reason`, `status` (`pending`/`approved`/`rejected`/`cancelled`), `current_step`, `requested_by`, `cancelled_by`/`cancelled_at`, `limit_override_reason` nullable, timestamps. One non-cancelled, non-rejected request per employee per date.

**`overtime_settings`** — one row: rates, night window, daily overtime cap, daily total cap, claim window days, TOIL ratio, TOIL block minutes, TOIL leave type id. Changing a rate applies to days rebuilt afterwards; already-paid months are payroll's history, not this table's.

**`daily_attendances`** — alter-migration adding the three overtime columns.

**`leave_adjustments`** — alter-migration adding nullable `overtime_request_id`.
